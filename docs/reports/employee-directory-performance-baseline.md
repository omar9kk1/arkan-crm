## 2. التشخيص المؤكد (EXPLAIN ANALYZE — قراءة فقط)

| الاستعلام | زمن التنفيذ | أبرز العقد |
|---|---:|---|
| صفحة OWNER clientsCount | **70.7 ms** | Hash Join 58.5 · Hash 52.8 · Aggregate 50.0 (4,501 صفًا) |
| ملخص OWNER | **67.7 ms** | Aggregate 67.1 · Hash Join 66.5 · Hash 43.1 |
| صفحة MANAGER clientsCount | 29.3 ms | Aggregate 26.1 (2,476 صفًا) |
| ملخص MANAGER | 40.2 ms | Aggregate 23.3 + Merge Join 22.3 (13,530 صفًا للمتأخرات) |

**الاختناق المؤكد:**
1. **تجميع العملاء الكامل يُنفَّذ مرتين** لنفس النطاق في أول صفحة (sort=clientsCount): مرة داخل استعلام الصفحة ومرة داخل الملخص. كل منهما يمسح 15,000 عميل عبر `UNION` ثم يجمّع لكل موظف.
2. **ملخص المتأخرات** (~20 ms) يُضاف فوق ذلك.
3. الاستعلامان يعملان **بالتوازي**، لذا زمن الجدار ≈ الأطول منهما (~44–70 ms)، وليس مجموعهما.

عدد استعلامات الخدمة لكل أول صفحة: **7** (صفحة + `user.findMany` وعلاقاته + مقاييس الصفحة + ملخص؛ المصادقة خارج القياس هنا لأن Task 20 جعلها استعلامًا واحدًا).

## 3. التحسين الذي جُرّب وأُلغي

**الفكرة:** في أول صفحة بلا فلاتر ومع `sort=clientsCount`، يُدمج الملخص داخل استعلام الصفحة (إعادة استخدام `counted` + CTE للمتأخرات + أعمدة ملخص كـscalar subqueries)، فيُحذف استعلام الملخص ويُوفَّر مسح العملاء المكرر.

**الصحة:** طابقت 16 حالة (OWNER/MANAGER × default/clients/properties/deals/active/inactive/search/cursor) **حقلًا بحقل** مع النسخة القديمة، و3 صفحات لكل دور بلا تكرار وبترتيب صحيح. الملخصات مطابقة تمامًا:
- OWNER: 5,000 / 4,801 / 13,535 / 7,746
- MANAGER: 2,750 / 2,641 / 7,460 / 4,264

**الأداء (A/B متناوب على مستوى الخدمة، نفس العملية/القاعدة، 12 تكرارًا):**

| الدور | القديم median | الجديد median | أفضل حالة قديم→جديد |
|---|---:|---:|---:|
| OWNER | 82.5 ms | **93.7 ms (+14%)** | 44.6 → 57.0 (+28%) |
| MANAGER | 69.5 ms | **71.7 ms (+3%)** | 40.0 → 50.5 (+26%) |

HTTP (نفس الـharness، CPU 10–15%):
- فردي: `owner.clients` 59.0 → 69.0 ms، `manager.clients` 51.3 → 57.1 ms.
- 10 طلبات: 24.87 → 36.88 RPS (إشارة متقلبة/باردة).
- **50 طلبًا: 50.7 → 28.9 RPS، P50 924.1 → 1,650.4 ms** (تراجع واضح).

**السبب:** الدمج حوّل تجميعين متوازيين إلى مسار متسلسل داخل اتصال واحد؛ انخفض إجمالي العمل قليلًا لكن **زمن احتجاز الاتصال لكل طلب ارتفع**، فساء الطابور عند 10 اتصالات. لذلك **لا يوجد تحسين آمن ومقاس بهذا الشكل**.

**التراجع:** أُعيد الكود الأصلي، والتطابق مثبت: ملف `dist-verify/employees/employees.service.js` بعد التراجع **مطابق بايت-ببايت** (نفس SHA-256) لبناء ما قبل التجربة. اختبارات الدليل: **4 suites / 39 اختبارًا ناجحًا**، typecheck وESLint نظيفان.

**النتيجة: لا تغيير إنتاجي.**

## 5. القيود والخطوة التالية

1. **لا تدمج الصفحة والملخص** في استعلام واحد: القياس يثبت أن التوازي أفضل رغم تكرار العمل.
2. **الهدف الصحيح التالي:** تسريع تجميع `client_pairs` نفسه مع إبقاء الاستعلامين متوازيين — مثل `UNION ALL` + `COUNT(DISTINCT id)` بدل `UNION` (تجنب إزالة التكرار المسبقة)، أو فصل المسارين (منشئ/مسؤول) والجمع، مع قياس A/B متناوب على مستوى الخدمة قبل/بعد.
3. **بديل منتجي** إن قبل المنتج: عدم حساب الملخص في كل أول صفحة (أو طلبه فقط عند عرضه) — قرار منتج لا تغيير تقني صامت.
4. أي تحسين لاحق يجب أن يُقاس بنفس منهجية A/B المتناوب + 50 طلبًا، لا بالاعتماد على جولات 100-user المتغيرة.
