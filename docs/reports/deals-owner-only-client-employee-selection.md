# معالج الصفقات: تجاوز موظف العميل للمالك فقط

**التاريخ:** 2026-11-11
**النطاق:** الخطوة 2 «اختيار العميل» في «تسجيل صفقة جديدة» — موظف العميل فقط.
**الحالة:** مكتمل، بدون ترحيل قاعدة بيانات وبدون تغيير أي بيانات أعمال حقيقية.

---

## 1. السبب الجذري

- مكوّن `EmployeeSelection` أصبح يدعم `allowOverride` بعد تقييد موظف العقار، لكن الخطوة 2 في `deal-create-wizard.tsx` لم تمرّر الخاصية، فبقيت قيمتها الافتراضية `true` وظهر «اختيار موظف آخر» للمدير أيضاً.
- الخادم كان يتحقق فقط من أن `clientEmployeeUserId` موظف نشط ضمن فريق المدير (`resolveEmployee`)، دون مقارنته بالموظف المسؤول الفعلي المسجّل على العميل المختار. أي أن المدير كان يستطيع استبدال موظف العميل بزميل آخر من فريقه.

**الحل:** تمرير `allowOverride={isOwner}` في الخطوة 2، ومزامنة إسناد المدير تلقائياً مع الموظف المسؤول الفعلي، وفرض المساواة على الخادم بـ **403**.

## 2. الملفات المتغيرة

| الملف | التغيير |

| `apps/frontend/features/manager-deals/components/employee-selection.tsx` | تحديث تعليق الخاصية لتشمل موظف العقار وموظف العميل (لا تغيير سلوكي) |

| `apps/backend/test/deals.spec.ts` | موظف ثانٍ في فريق المدير + اختبار تجاوز موظف العميل للمالك/المدير، والتحقق من عدم تغيير الإسناد الدائم والعمولات |

لا تغيير على CSS أو التصميم أو الخطوات 1 و3 و4.

## 3. مصفوفة الصلاحيات

### الواجهة

| الدور | الخطوة 1 (موظف العقار) | الخطوة 2 (موظف العميل) |
|---|---|---|
| OWNER | «اختيار موظف آخر» ظاهر وفعّال | «اختيار موظف آخر» ظاهر وفعّال |
| MANAGER | مخفي، الموظف الحالي للقراءة فقط | مخفي، الموظف المسؤول الفعلي للعميل يُعرض تلقائياً للقراءة فقط |

- «اعتماد الموظف» باقٍ في الحالتين كما هو.
- التحقق من الانتقال للمراجعة ما زال يمنع المتابعة بدون موظف معتمد.

### الخادم

| الحالة | النتيجة |
|---|---|
| OWNER يرسل أي `clientEmployeeUserId` لموظف نشط | مسموح (تجاوز مصرّح) |
| MANAGER يرسل الموظف المسؤول الفعلي للعميل | مسموح |
| MANAGER يرسل موظفاً آخر من فريقه | **403** |
| MANAGER يرسل موظفاً من فريق آخر | **403** |
| MANAGER يرسل عميلاً غير مصرّح | **404** (من `clientOwnershipWhere`) |
| عميل بلا موظف مسؤول + مدير | مرفوض بالقواعد الحالية (لا يُختلق موظف ولا يُسند تلقائياً) |

- التحقق يتم داخل نفس معاملة الإنشاء وقبل الاستحواذ على حالة العقار، فلا توجد كتابة جزئية عند الرفض.
- لا يتم تحديث `Client.responsibleEmployeeId` ولا `Property.createdByUserId` عند تسجيل الصفقة.
- توزيع العمولات ودقة KWD وعزل الفرق لم تتغير.

## 4. الاختبارات والنتائج الفعلية

بيئة الكتابة: `arkan_crm_api_test` فقط.

| `npm run typecheck -w @arkan/frontend` | 0 |
| `npx eslint apps/backend/src/deals apps/backend/test/deals.spec.ts apps/frontend/features/manager-deals` | 0 |

الاختبار الجديد `allows OWNER to override the client employee while MANAGER cannot` يغطي:

1. المدير ينشئ صفقة بالموظف المسؤول الفعلي → 201، و`clientEmployee` الصحيح.
2. `Deal.clientEmployeeId` وسطر عمولة `CLIENT_EMPLOYEE` يشيران إلى ملف الموظف الفعلي.
3. محاولة استبداله بزميل من **نفس الفريق** → **403**.
4. محاولة استبداله بموظف من **فريق آخر** → **403**.
5. المالك يستبدل موظف العميل بموظف OWNER-direct → 201 والإسناد الصحيح.
6. `Client.responsibleEmployeeId` و`Property.createdByUserId` لم يتغيرا بعد كل ذلك.

اختبارات الصفقات السابقة (11) بقيت ناجحة: البحث والترقيم، عزل الفرق، تجاوز موظف العقار، دقة المبالغ، التزامن، ولوحة المعلومات.

## 5. قيود متبقية

- إذا كان العميل بلا موظف مسؤول (عميل أنشأه مدير دون إسناد)، فلا يستطيع المدير إنشاء صفقة عليه لأن `clientEmployeeUserId` مطلوب في القواعد الحالية. هذا سلوك مقصود: لا يتم اختلاق أو إسناد موظف تلقائياً. المالك يستطيع الإسناد يدوياً ضمن صلاحية التجاوز.
- إخفاء الزر في الواجهة إجراء دفاعي؛ المرجع النهائي هو تحقق الخادم.
- لم تُجرَ جولة نقر يدوية في المتصفح ضمن هذه المهمة؛ الأدلة هي اختبارات API فعلية + typecheck + lint، وفحص مسار الواجهة في الكود (تمرير `allowOverride` في الخطوتين).
- لا ترحيل قاعدة بيانات ولا تفعيل جديد مطلوب.
