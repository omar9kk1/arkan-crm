# خطة تنظيف المالكين المكررين — قاعدة التطوير

- **التاريخ:** 2026-10-20
- **النطاق:** قاعدة بيانات التطوير `arkan_crm` (قراءة فقط — لم يُكتب أي شيء)
- **الحالة:** مسودة بانتظار الموافقة. **لا تنفيذ قبل الاعتماد.**

---

## 1. الملخّص التنفيذي

| البند | القيمة |
|---|---|
| عدد جهات اتصال OWNER | 11 |
| عدد جهات اتصال BROKER | 0 |
| عدد الموظفين المالكين لجهات OWNER | موظف واحد فقط (`employee@arkan.test` / `mohamed`) |
| مجموعات مكرّرة مؤكَّدة | 4 |
| سجلات مكرّرة قابلة للدمج | 7 (تبقى 4 سجلات أساسية) |
| عقارات تحتاج إعادة ربط `contactId` | 5 |
| سجلات يتيمة (0 عقار) | 7 |
| النتيجة المتوقّعة بعد التنظيف | 4 جهات OWNER بدل 11، كل واحدة مرتبطة بعدد العقارات الصحيح |

**سبب التكرار:** خلل في مسار تعديل العقار كان يبني النموذج على «مالك جديد» فيهرب `newContact` للخلفية، فتُنشأ جهة اتصال جديدة ويُنقل `Property.contactId` إليها بينما يبقى السجل القديم بلا عقارات. أُصلح الكود لاحقًا، لكن السجلات المُنشأة قبله ما زالت موجودة وتحتاج تنظيفًا يدويًا.

## 2. تحقّق السلامة (قبل أي كتابة)

تم فحص جميع المراجع الخارجية (Foreign Keys) المرتبطة بجدول `Contact`:

| الجدول / العمود | يشير إلى | قاعدة الحذف | صفوف تشير إلى Contact |
|---|---|---|---|
| `Property.contactId` | `Contact.id` | `RESTRICT` | نعم — 6 عقارات |
| `Property.ownerId` | جدول `Owner` القديم | — | 0 صفوف (الجدول فارغ) |
| `FollowUp.ownerId` | جدول `Owner` القديم | — | 0 صفوف |
| `Notification.ownerId` | جدول `Owner` القديم | — | 0 صفوف |

نتائج إضافية:
- **لا توجد أي صفوف `AuditLog`** بنوع `entityType = 'Contact'` — لا يوجد تاريخ تدقيق مطلوب الحفاظ عليه على مستوى جهة الاتصال.
- **لا توجد حقول `notes`** مملوءة على أي من جهات الاتصال الـ 11 (كلها فارغة).
- `Notification` ترتبط بـ`propertyId` لا بـ`contactId`، فلا تتأثر بالدمج.
- لا قيود فريدة (Unique) على `Contact` عدا المفتاح الأساسي `id`.
- لا توجد جداول علاقات أخرى (علاقات جهات الاتصال غير موجودة في المخطط الحالي).
- **الأسماء والأرقام متطابقة حرفيًا (بايت‑ببايت)** داخل كل مجموعة — لا فراغات زائدة ولا أرقام مقنّعة مختلفة.

> الخلاصة: البنية الحالية تسمح بدمج آمن عبر **إعادة ربط العقارات ثم حذف السجلات اليتيمة** فقط، دون فقدان أي بيانات.

**نطاق الموظف:** جميع المجموعات الأربع تخصّ الموظف نفسه `1f040211-9c75-4e57-b0a8-aad4b9a9f88b`. لا يوجد أي تشابه بين موظفين مختلفين، لذا لا تنشأ أي مشكلة خصوصية في هذا التنظيف. (لو ظهر لاحقًا رقم مشترك بين موظفين مختلفين، فيجب إبقاؤهما منفصلين تمامًا — غير مطبّق هنا.)

## 7. المخاطر والتخفيف

| المخاطرة | التخفيف |
|---|---|
| دمج سجلين يعودان لشخصين مختلفين | تحقّق مزدوج: تطابق الاسم **و** الرقم **و** نفس الموظف؛ لا دمج عند الشك |
| فقدان تاريخ/ملاحظات | كل حقول `notes` فارغة، ولا تدقيق على `Contact`؛ لا بيانات تُفقد |
| كسر مرجع `RESTRICT` | إعادة الربط تتم **قبل** الحذف داخل نفس المعاملة |
| المساس بمسار الموافقة | لا تُعدَّل `Property.status` ولا `PropertyApprovalRequest` إطلاقًا |
| تسريب بيانات بين موظفين | جميع المجموعات لنفس الموظف؛ لا تقاطع أصلي |
| خطأ غير متوقّع | نسخة احتياطية مُتحقَّق منها + معاملة واحدة + `ROLLBACK` عند فشل أي فحص |
| تكرار مستقبلي | أُصلح الكود مسبقًا؛ التنظيف لمرة واحدة فقط |

## 8. ما لم يُنفَّذ (متعمَّد)
- لا حذف ولا دمج ولا تعديل على قاعدة التطوير.
- لا تغيير في حالات العقارات أو سير الموافقات.
- لا تعديل على كود التطبيق أو مخطط Prisma أو الواجهة.
- لا التزامات (commits) ولا دفع (pushes) ولا أوامر تنظيف.

**الحالة: متوقف قبل أي كتابة على قاعدة البيانات — بانتظار الموافقة.**
