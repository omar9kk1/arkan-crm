# سجل النظام — درج تفاصيل المراجعة للقراءة فقط

**التاريخ:** 2026-11-11  
**المشروع:** `D:\Projects\arkan-crm`  
**النطاق:** جعل بطاقات OWNER ← الإشعارات ← سجل النظام قابلة للفتح على درج تفاصيل المراجعة الحقيقي، بوضع قراءة فقط.  
**الحالة:** مكتمل.

---

## 1. المكوّنات المعاد استخدامها

لم يُبنَ درج بديل. أُعيد استخدام:

- `ClientReviewDetailsDrawer` — نفس درج مراجعة العميل الذي يستخدمه المدير.
- `PropertyDetailsDrawer` — نفس درج تفاصيل/مراجعة العقار الحالي.
- `PropertyOverlay` — للتحميل/الخطأ/الإغلاق من اليسار وEscape.
- `GET /client-reviews/:id` — تفاصيل طلب مراجعة العميل (OWNER لديه وصول كامل).
- `GET /properties/:id` — تفاصيل العقار الحقيقي.
- `mapPreviewFromApi` — تحويل استجابة العقار إلى نموذج العرض الحالي.

أُضيف فقط:

- `SystemLogDetailsDrawer` — جسر صغير يقرأ المعرّف ويعرض أحد الدرجين.
- حقول `details` في استجابة سجل النظام.
- وضع `readOnly` صريح في الدرجين المشتركين.

---

## 2. ربط حدث السجل بالطلب الحقيقي

أصبح كل صف في سجل النظام يحمل:

```ts
details: {
  type: 'CLIENT_REVIEW' | 'PROPERTY';
  id: string;
} | null
```

المصدر هو `AuditLog.entityType` و`AuditLog.entityId` الموثوقان:

- `entityType = 'ClientReviewRequest'` → `details.id = ClientReviewRequest.id`.
- `entityType = 'Property'` → `details.id = Property.id`.
- غير ذلك → `details = null` ولا تصبح البطاقة قابلة للفتح.

لا يوجد بحث بالاسم، ولا مطابقة تخمينية، ولا فتح لسجل غير مرتبط.

أمثلة:

- «محمد أرسل عميلاً للمراجعة» → `CLIENT_REVIEW` بنفس `reviewId`.
- «المدير وافق على طلب عميل» → نفس `reviewId` بحالته الحالية.
- «تمت الموافقة على عقار» → `PROPERTY` بنفس `propertyId`.

## 3. الواجهة

- بطاقات سجل النظام المدعومة أصبحت:
  - قابلة للنقر.
  - قابلة للوصول بلوحة المفاتيح (`Enter` / `Space`، `role=button`، `tabIndex=0`).
  - تحمل شارة «عرض التفاصيل».
- غير المدعوم (مثل تعيين مدير/صلاحيات) يبقى غير قابل للفتح.
- الدرج يفتح من **اليسار** عبر `PropertyOverlay` الموجود.
- الإغلاق بزر الإغلاق أو `Escape` يعيد التركيز ويحافظ على حالة تبويب سجل النظام، الفلاتر، الصفحات، وموضع التمرير لأن قائمة السجل لا تُعاد بناؤها.
- حالة تحميل، خطأ مع إعادة المحاولة، وسجل غير متاح كلها داخل نفس الدرج.
- لم يُغيَّر تبويب «الإشعارات» أو تصميم البطاقات أو ألوان/خطوط/RTL.

## 4. فرض القراءة فقط

### درج مراجعة العميل

أُضيف `readOnly` و`error` إلى `ClientReviewDetailsDrawer`:

- عند `readOnly` لا تُعرض أزرار:
  - موافقة / رفض / طلب تعديل.
  - إعادة إرسال.
  - أي حقل ملاحظات قرار.
- يظهر بدلًا منها نص:
  > عرض للقراءة فقط من سجل النظام — لا توجد إجراءات متاحة. الحالة المعروضة هي الحالة الحالية للطلب وقد تختلف عن لحظة الحدث.
- لا تُستدعى دوال القرار من هذا الوضع؛ الجسر يمرر دوال no-op فقط، والفرع الذي يعرض الأزرار لا يُنفَّذ أصلًا.

### درج العقار

أُضيف `readOnly` إلى `PropertyDetailsDrawer`:

- لا يُمرَّر `onAction`، ولا `onApproveDistinct`، و`canDelete=false`.
- يظهر تنبيه قراءة فقط أعلى المحتوى.
- لا توجد أزرار موافقة/رفض/طلب تعديل/حذف/استعادة.
- قسم مقارنة التكرار المعروض للقراءة فقط لا يحتوي أزرار قرار.

### فتح/إغلاق الدرج

الجسر لا يستدعي إلا:

- `GET /client-reviews/:id`
- `GET /properties/:id`

ولا يستدعي أي mutation endpoint. اختبار العدّادات قبل/بعد القراءات أثبت عدم تغيّر:
`ClientReviewRequest`, `Client`, `Notification`, `Property`.

## 5. الصلاحيات والأمان

- سجل النظام نفسه OWNER فقط عبر `@Roles(Owner)` و`assertOwner`.
- `GET /client-reviews/:id` يسمح لـOWNER بكل الطلبات (`reviewScopeWhere = {}`).
- `GET /properties/:id` يعيد العقار لمالك النظام ضمن نطاقه الكامل.
- MANAGER/EMPLOYEE لا يستطيعون الوصول إلى `/notifications/system-log` (403)، وبالتالي لا يستطيعون فتح هذا المسار من الواجهة.
- لم تُوسَّع صلاحيات MANAGER/EMPLOYEE.
- الاستجابة تحمل فقط `type` و`id`؛ لا JSON خام من AuditLog ولا حقول داخلية.

## 6. الاختبارات والتحقق

```text
3 suites / 21 tests passed
review-routing-system-log.spec.ts
+ client-review-workflow.spec.ts
+ client-edit-notifications.spec.ts

backend typecheck: 0
frontend typecheck: 0
targeted ESLint: 0
```

غطّت الاختبارات:

- سجل النظام يعيد `details` الصحيحة لمراجعة العميل والعقار.
- OWNER يقرأ تفاصيل المراجعة الحقيقية (`200`).
- OWNER يقرأ تفاصيل العقار الحقيقي (`200`).
- الحالة الحالية تتغير من `PENDING` إلى `APPROVED` بعد القرار، والتفاصيل تعرضها بدقة.
- حدث بعد الموافقة (`CLIENT_REVIEW_APPLY`) يشير لنفس `reviewId`.
- عدّادات قاعدة البيانات لا تتغير بعد قراءة التفاصيل.
- سجل تاريخي بمعرّف غير موجود → `details=null` ولا تُفتح بطاقة.
- MANAGER/EMPLOYEE → 403 على سجل النظام، وبدون مصادقة → 401.
- الأحداث غير المرتبطة (تعيين مدير/صلاحيات) تبقى بدون رابط تفاصيل.

## 7. القيود والملاحظات

- **درج العقار** يعرض الحالة الحالية وآخر ملاحظات المراجعة من نفس واجهة تفاصيل العقار الموجودة؛ لا يعرض كل جولات المراجعة التاريخية. هذا هو أصغر إعادة استخدام آمنة بدون إعادة بناء واجهة المراجعة. الأحداث نفسها تظل ظاهرة في سجل النظام.
- **درج مراجعة العميل** يعرض الطلب الكامل والاقتراح والحالة الحالية وملاحظات المراجعة، وليس لقطة تاريخية مجمّدة؛ التنبيه داخل الدرج يوضح ذلك.
- السجل التاريخي الذي فقد سجله المرتبط (عقار محذوف نهائيًا، مرجع ناقص) لا يفتح تخمينًا؛ تظهر حالة «غير متاح» أو لا تصبح البطاقة قابلة للفتح.
- أحداث نقل العقار إلى المحذوفات لا تعرض رابط تفاصيل لأن `GET /properties/:id` يخفي الصفوف المحذوفة عمدًا؛ تبقى البطاقة مقروءة في السجل بدون رابط مكسور.
- لا migration، ولا تغيير في بيانات الأعمال، ولا تغيير في منطق الموافقة/الرفض أو توجيه الإشعارات.
- لا commits أو pushes.

**النتيجة: مكتمل — متوقف للمراجعة اليدوية.**
