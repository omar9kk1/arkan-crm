# مقترح تصميم: خصوصية سجلات الموظف والهوية المشتركة — Arkan CRM

- **التاريخ:** 2026-10-19
- **النوع:** تحليل معماري فقط (**لا تنفيذ، لا تعديل مخطط، لا تعديل بيانات، لا دمج أو حذف لجهات التواصل، لا commits**)
- **الحالة:** `Completed` (تحليل) — كل بنود التنفيذ `Not Implemented (بانتظار الموافقة)`
- **القاعدة التجارية المعتمدة:** كل موظف يصل فقط إلى سجلاته أو السجلات المُسنَدة إليه صراحةً؛ لا يُكشف للموظف وجود نفس الشخص عند موظف آخر؛ المدير يرى كل العلاقات ويتعرّف على الهويات المشتركة الموثّقة؛ ولا دمج تلقائي بالاسم أو الهاتف.

---

## 1. النموذج الحالي (ما هو موجود فعليًا في الكود)

| الكيان | العلاقة الفعلية | ملاحظة |
| --- | --- | --- |
| `User` | `role: MANAGER \| EMPLOYEE`، `employeeProfile` اختياري | مصدر الهوية للتفويض |
| `EmployeeProfile` | مرتبط بـ`User`؛ يحمل `createdClients/createdOwners/createdProperties/assignments` | الموظف موجود فقط عند وجود ملف موظف |
| `Contact` | `type`، `name`، `phone`، **`responsibleUserId (User.id)`**، `properties Property[]` | العلاقة الحالية الوحيدة لجهة التواصل؛ لا يوجد أي مفهوم هوية مشتركة |
| `Property` | `contactId → Contact?` (علاقة التواصل)، `ownerId → Owner?` (قديم)، `createdByUserId → User?` | المصدر المعتمد لعدّ العقارات هو `Property.contactId` |
| `Client` | `createdById/responsibleEmployeeId → EmployeeProfile?` | كيان منفصل عن `Contact` ولا يرتبط بالعقارات |
| `PropertyAssignment` | `propertyId + employeeId + purpose` بفهرس فريد | **الأساس الجاهز للإسناد الصريح** (نوع المهمة يحدد الغرض) |

### قواعد التفويض الحالية (خلفية)

- جهات التواصل: `contactOwnershipWhere` → المدير: بلا قيد؛ الموظف: `{ responsibleUserId: viewer.id }`. سجل بدون مسؤول (سجل شركة) **لا يُرى للموظف إطلاقًا** (منع افتراضي).
- العقارات: `propertyVisibilityWhere` → الموظف يرى `AVAILABLE` (أي مُنشئ) + عقاراته `PENDING/REJECTED`؛ و`SOLD/RENTED/ARCHIVED` تمنع افتراضيًا.
- العدّ المعروض على الكروت: `ContactDto.properties` محسوب داخل استعلام Prisma بنفس فلتر رؤية العقار أعلاه (لا عدّ على الواجهة، ولا مطابقة بالاسم).
- لا يوجد أي مسار في الكود يطابق أو ينشئ جهات تواصل بالاسم؛ الإنشاء يحدث صراحةً عند `newContact` أو اختيار جهة قائمة بـ`contactId`.

## 2. كيف تُنشأ سجلات المالك المكرّرة حاليًا (سبب مؤكَّد بالكود والبيانات)

1. **المعالج عند التعديل يفقد ارتباط جهة التواصل:** `formFromPropertyV2` في `apps/frontend/features/employee-properties/components/new-property-modal-v2.tsx` يعيد النموذج دائمًا بـ`ownerMode: 'NEW'` و`ownerId: ''`. لذلك أي «تعديل/إعادة إرسال» لعقار مرتبط يرسل `newContact`.
2. **الخلفية تنشئ سجلًا جديدًا فعليًا:** `resolveContactInTx` (إنشاء) وكتلة `payload.newContact` (تحديث) في `apps/backend/src/properties/properties.service.ts` تستدعيان `tx.contact.create(...)` ثم تُعيدان ربط `Property.contactId` بالسجل الجديد. النتيجة: سجل قديم يتيم (0 عقارات) + سجل جديد يحمل العقار (1 عقار).
3. **قائمة «المالك المسجّل» ناقصة للموظف:** قائمة الاختيار تأتي من `GET /contacts?type=OWNER` بفلتر الملكية، وسجلات الشركة (`responsibleUserId = null`) غير مرئية للموظف؛ فلا يجد المالك، فيُدخله كن جديد → سجل شركة/موظف آخر.
4. **لا يوجد كشف تكرار فعّال:** تنبيه «يوجد مالك مسجل بنفس رقم الهاتف» في المعالج يعتمد على القائمة المفلترة نفسها (`findContactByPhone` على `contactRecords`)، فلا يُنذر بوجود الشخص عند موظف آخر.

**الدليل على قاعدة التطوير (قراءة فقط، أسماء مقنّعة):** 7 سجلات `OWNER`، 6 عقارات كلها مرتبطة، لا سجلات شركة، لا `Property.ownerId`، ولا عقار بلا ارتباط. ثلاث مجموعات هاتف متطابقة (بعد تجريد غير الأرقام) فيها سجّلان لكل شخص بنفس الاسم والنوع: (9485 → 1+0)، (8882 → 1+1)، (3535 → 1+1) ⇒ 6 سجلات = 3 أشخاص حقيقيين. الجدول الزمني يثبت سيناريو التعديل: سجل أُنشئ مع العقار في `2026-10-16 00:02:26`، وسجل ثانٍ أُنشئ في `2026-10-19 00:56:35` والعقار نفسه `updatedAt = 00:57:00`.

> ملاحظة: التكرار «الحقيقي» لا يُميَّز بالاسم وحده؛ التطابق الحالي يدعم نفس `type` + نفس الهاتف المعياري، ويبقى قرار التوحيد بشريًا.

## 3. أصغر نموذج بيانات آمن مقترح

المبدأ: **لا نلمس `Contact` الحالي ولا `Property.contactId`**؛ نضيف طبقتين أفقيتين: هوية داخلية (مدير فقط) + إسناد صريح للموظف.

### 3.1 كيان الهوية الداخلية (جديد)

```prisma
enum PersonIdentityStatus {
  UNVERIFIED   // ترشيح آلي، غير مؤكد
  VERIFIED     // أكّده المدير بعد مراجعة الأدلة
  REJECTED     // ليس نفس الشخص
}

model PersonIdentity {        // لا يُعاد أبدًا لأي نقطة نهاية يستدعيها الموظف
  id            String               @id @default(uuid()) @db.Uuid
  displayName   String               // الاسم المعتمد داخليًا للمدير
  status        PersonIdentityStatus @default(UNVERIFIED)
  verifiedById  String?              @db.Uuid
  verifiedBy    User?                @relation("IdentityVerifier", fields: [verifiedById], references: [id], onDelete: Restrict)
  verifiedAt    DateTime?
  createdAt     DateTime             @default(now())
  updatedAt     DateTime             @updatedAt
  contacts      Contact[]            // علاقة عكسية فقط
  @@index([status])
}

model ContactIdentityLink {   // شواهد الربط، قابلة للتتبع والتراجع
  contactId  String   @id @db.Uuid
  contact    Contact  @relation(fields: [contactId], references: [id], onDelete: Cascade)
  identityId String   @id @db.Uuid
  identity   PersonIdentity @relation(fields: [identityId], references: [id], onDelete: Restrict)
  matchedBy  String   // 'PHONE_EXACT' | 'PHONE_LAST8' | 'MANUAL' ...
  matchedAt  DateTime @default(now())
  @@id([contactId, identityId])
  @@index([identityId])
}
```

التغيير الوحيد على `Contact`: إضافة `identityLinks ContactIdentityLink[]` (حقل عكسي، بلا ترحيل بيانات). مفتاح الربط يبقى `Contact.id` كما هو اليوم.

### 3.2 الإسناد الصريح للموظف (بلا جدول جديد)

- إعادة استخدام `PropertyAssignment` بغرض جديد (`AssignmentPurpose.MARKETING` أو إضافة قيمة `RESPONSIBLE`) لتمثيل «موظف مسؤول عن العقار».
- رؤية الموظف للعقار = عقاراته (`createdByUserId = viewer.id`) **أو** عقار له `PropertyAssignment.employeeId = profile(viewer).id` — إضافة شرط `OR` إلى `propertyVisibilityWhere` فقط.
- جهة التواصل ترث الرؤية من العقار: الموظف يرى سجل تواصل إذا كان `responsibleUserId = viewer.id` (كما اليوم) **أو** كان مرتبطًا بعقار يراه. بهذا يرى الموظف «عقارات وجهات التواصل المُسنَدة إليه» دون أي تغيير على البيانات القائمة.

### 3.3 العدّ داخل نطاق الموظف والعدّ الكلي للمدير

- **الموظف (كما اليوم):** `ContactDto.properties` = `Property.contactId = contact.id` **مفعَّل بنفس فلتر رؤية العقار** ⇒ العدّ = ما يستطيع الموظف فتحه فعلًا فقط. لا تُضاف أي معلومات عن سجلات الآخرين.
- **المدير (جديد ومقيَّد):** حقول إضافية على `ContactDto` للمدير حصرًا:
  - `identity: { id, status } | null` — إن كان السجل مرتبطًا بهوية داخلية.
  - `companyPropertyCount: number` — عدد عقارات كل السجلات المرتبطة بنفس الهوية الموثّقة (`VERIFIED`) داخل الشركة، **رقم مُجمَّع فقط**.
- الموظف **لا يستلم** هذه الحقول أبدًا (تُبنى فقط عند `viewer.role === MANAGER`)، فلا تتسرب الأعداد عبر الواجهة.
- أثناء `UNVERIFIED` (قبل اعتماد المدير) يظهر للمدير عدد «سجلات مرشّحة» فقط، دون أي دمج.

### 3.4 الفهرسة المطلوبة (بلا تغيير سلوكي)

`PersonIdentity(status)`؛ `ContactIdentityLink(identityId, contactId)`؛ وفهرس مساعد إن لزم للمطابقة: `Contact(type, phone)` — الأخير **ليس ضروريًا** لأن `@@index([phone])` قائم، ويُقاس الحجم قبل إضافته.

## 4. حفظ السجلات الحالية وربطها بأمان (بلا حذف أو دمج)

1. **لا حذف ولا تعديل لأي `Contact` أو `Property`**؛ الهوية طبقة إضافية فقط.
2. `PersonIdentity` يُنشأ فارغًا، ثم تُضاف الروابط عبر `ContactIdentityLink` بسجل تدقيق لكل ربط.
3. الترتيب المقترح للترحيل الآمن: (أ) إضافة المخطط، (ب) سكربت **ترشيح فقط** يقترح مجموعات (نفس `type` + نفس الرقم المعياري) بحالة `UNVERIFIED`، (ج) المدير يعتمد يدويًا فيصبح `VERIFIED`، (د) أي اعتماد خاطئ يُلغى بحذف صف الربط وحده (لا أثر على البيانات).
4. العقارات لا تُنقل: كل عقار يبقى على `contactId` الحالي؛ العدّ الكلي للمدير يُشتق من روابط الهوية أثناء الاستعلام.
5. السجلات «اليتيمة» الحالية تُترك كما هي؛ تُعرَض للمدير في تقرير مراجعة (قراءة فقط) ولا تُدمج آليًا.

## 5. قواعد التفويض وكشف التكرار (خلفية)

**التفويض (منع افتراضي):**
- المدير: كل السجلات + حقول الهوية/العدّ الكلي.
- الموظف: `responsibleUserId = viewer.id` أو عبر إسناد عقار صريح فقط. أي معرّف غير مصرّح ⇒ **404** بلا تمييز (كما هو السلوك الحالي)، ويُطبَّق **قبل** أي حساب للعدّ.
- `ContactDto` للموظف لا يحمل `identity` ولا `companyPropertyCount` ولا عدد سجلات الآخرين.

**كشف التكرار (داخلي فقط):**
- على الخلفية، عند إنشاء `Contact` جديد (وما يعادله في المعالج)، تُحسب مطابقة على مستوى الشركة:
  1. مطابقة قوية: نفس `type` + نفس الرقم المعياري (أرقام فقط).
  2. مطابقة ضعيفة: آخر 8 أرقام + تطابق الاسم المعياري (مسافات/تشكيل).
- عند وجود مطابقة: يُنشأ/يُحدَّث `PersonIdentity` بحالة `UNVERIFIED` وربط **داخلي** فقط.
- **استجابة الموظف لا تتغير إطلاقًا** (نجاح عادي، بلا أي رسالة تكرار) — يتحقق شرط «لا كشف لوجود الشخص عند موظف آخر».
- الاستثناء المسموح: إن كانت المطابقة **داخل سجلات نفس الموظف**، يجوز إظهار تنبيه محلي داخل نطاقه فقط («لديك مالك مسجّل بنفس الرقم: …») مع زر «استخدام السجل الموجود» — هذا ما يحقق «تفادي التكرار داخل سجلات الموظف نفسه».
- **لا دمج تلقائي أبدًا**؛ التوحيد لا يحدث إلا باعتماد المدير (`VERIFIED`)، ولا ينقل أي عقار.
- **تحصين القنوات الجانبية:** البحث (يظل مقيّدًا بنطاق الموظف)، رسائل التحقق (لا رسالة «مسجّل مسبقًا»)، الأعداد في `ContactDto`، وكل نقاط النهاية — لا تكشف وجود سجل خارج نطاق الموظف، والاختبارات تُثبت ذلك صراحةً.

## 6. الترحيلات والواجهات والاختبارات المطلوبة

**Prisma/DB (ترحيل واحد إضافي، آمن):**
- `PersonIdentity` + `ContactIdentityLink` + علاقة عكسية على `Contact` + `enum PersonIdentityStatus`.
- اختياري لاحقًا: قيمة غرض جديد في `AssignmentPurpose` إن لم يكفِ `MARKETING` الحالي (يُقرَّر قبل التنفيذ).
- لا تعديل على أعمدة قائمة، ولا `NOT NULL` جديد، ولا حذف جداول.

**APIs:**
- (إلزامي) توسيع `GET /contacts` و`GET /contacts/:id` بحقول المدير `identity` و`companyPropertyCount` فقط عند `MANAGER`.
- (إلزامي) توسيع `propertyVisibilityWhere` بشرط الإسناد الصريح، وثمّ ترث جهة التواصل الرؤية عبر العقار.
- (مدير فقط) `GET /identities?status=UNVERIFIED` — قائمة ترشيحات للمراجعة.
- (مدير فقط) `POST /identities/:id/verify` و`POST /identities/:id/reject` — اعتماد/رفض مع سجل تدقيق.
- (مدير فقط) `GET /identities/:id` — كل السجلات والعقارات المرتبطة داخل الشركة.
- (بلا كشف) إنشاء جهة تواصل: نفس الاستجابة الحالية بلا أي مؤشر مطابقة.

**اختبارات الانحدار (خلفية):**
1. مدير يرى `identity` و`companyPropertyCount` مجمّعين؛ موظف **لا** يستلم أي منهما (فحص مفاتيح الاستجابة).
2. موظف لا يرى أي أثر لسجل موظف آخر: لا في القائمة، لا في العدد، لا في 404 مقابل 403، ولا في رسائل التحقق.
3. موظف A ينشئ شخصًا موجودًا عند B ⇒ نجاح عادي بلا أي إشارة تكرار في الاستجابة.
4. مطابقة داخل سجلات نفس الموظف فقط ⇒ تنبيه مقترح بلا دمج تلقائي.
5. اعتماد المدير (`VERIFIED`) ⇒ يظهر العدّ الكلي المجمّع، وتُعزل حالة `REJECTED`.
6. العدّ لكل موظف = العقارات المرئية فقط (يشمل الإسناد الصريح، ويستثني `SOLD/RENTED/ARCHIVED` كما القاعدة الحالية).
7. تعديل عقار مرتبط لا يُنشئ جهة تواصل جديدة (اختبار انحدار لعيب المعالج) بعد إصلاحه.
8. اختبار تفويض لكل نقطة نهاية جديدة: الموظف ⇒ 403/404 بلا كشف.

**الواجهة (محدود):**
- بطاقة المالك/الوسيط: لا تغيير (العدّ الحالي باقٍ).
- إضافة شاشة/تبويب «هويات للمراجعة» للمدير فقط (تصميم Astra نفسه)، وخيار «عرض كل سجلات هذا الشخص» داخل ملف المدير.
- الموظف: يبقى كل شيء كما هو + تنبيه اختياري داخل نطاقه عند تكرار داخلي.

## 7. الحفاظ الصريح على المعالج والتصميم الحالي

- **معالج العقار:** يبقى مساره هو نفسه (`POST/PATCH /properties` بـ`contactId` أو`newContact`). التعديل المطلوب لاحقًا **إصلاح واحد محدود** لاستعادة `contactId` عند التعديل بدل `ownerMode: 'NEW'` — يُعرض كنقطة موافقة مستقلة ولا يُنفَّذ الآن.
- قائمة «المالك المسجّل»: تُوسَّع لاحقًا بخيار قراءة فقط لسجلات الشركة (بـ`scope=company`) بحيث تعمل فعليًا «استخدام السجل الموجود» — بلا أي تغيير على شكل المعالج أو خطواته.
- **تصميم Astra:** لا تغيير على `*.module.css`، ولا على كروت المالك/الوسيط، ولا على الأدراج الحالية؛ كل الإضافات واجهية داخل مكونات Astra القائمة.
- لا تغيير على العلاقات القائمة، ولا على `Owner` القديم، ولا على بيانات الإنتاج.

## 8. المخاطر والقرارات المطلوبة قبل التنفيذ

1. اختيار غرض الإسناد: قيمة `AssignmentPurpose` جديدة أم إعادة استخدام `MARKETING`؟
2. سياسة الإسناد: هل الإسناد يمنح رؤية العقار كاملة أم للقراءة فقط؟
3. إظهار التنبيه الداخلي للموظف: مُفعَّل افتراضيًا أم اختياري؟
4. مراجعة السجلات اليتيمة الحالية: تقرير فقط أم شاشة مراجعة للمدير؟
5. حجم البيانات المستقبلي ومقاييس فهارس المطابقة (يُقاس قبل الترحيل).
6. تأكيد أن كل من `docs/reports` لا يحتوي أي قيمة بيئة/أسرار (التزم بهذا التقرير).
