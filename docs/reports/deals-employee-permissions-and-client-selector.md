# معالج الصفقات: تجاوز الموظف للمالك فقط + اختيار عميل حقيقي قابل للبحث

**التاريخ:** 2026-11-11
**النطاق:** «تسجيل صفقة جديدة» — الخطوة 1 (الموظف المسؤول عن العقار) والخطوة 2 (اختيار العميل).
**الحالة:** مكتمل، بدون ترحيل قاعدة بيانات وبدون تغيير أي بيانات أعمال حقيقية.

---

## 1. السبب الجذري لعدم ظهور العملاء

1. الخطوة 2 كانت تعتمد على `GET /deals/options` فقط. هذه النقطة تُرجع **كامل** قائمة العملاء المصرّح لهم مرة واحدة، بلا بحث ولا ترقيم صفحات (`deals.service.ts → options`).
2. الواجهة كانت تعرض `<GlassSelect>` بسيطاً (قائمة HTML) بدون أي حقل بحث، لذلك أي قائمة طويلة أو غير محمّلة لا تعطي تجربة اختيار قابلة للاستخدام.
3. لا توجد نقطة قراءة مخصّصة للصفقات تسمح بالبحث على الخادم داخل نطاق العملاء المصرّح بهم.
4. في قاعدة البيانات الحقيقية `arkan_crm` حالياً **0 صفوف `Client`**، لذلك حتى بعد الربط الصحيح تظهر حالة «لا يوجد عملاء متاحون» وهي حالة صحيحة وليست خطأ. سجلات `ClientReview` المعلّقة/المرفوضة ليست صفوف `Client`، ولا يجوز أن تظهر في الاختيار.

**الحل:** إضافة `GET /deals/client-options` — نقطة قراءة صغيرة بصلاحية OWNER/MANAGER، ببحث وترقيم مؤشر (cursor) داخل نفس شرط الملكية المستخدم في `/clients`، وربط الخطوة 2 بها عبر `GlassCombobox` مع الحفاظ على الشكل الحالي.

## 3. قاعدة تجاوز الموظف (الخطوة 1)

| الدور | الواجهة | الخادم |
|---|---|---|
| OWNER | «اختيار موظف آخر» ظاهر وفعّال، مع «اعتماد الموظف» | تجاوز غير مقيّد ضمن الموظفين المؤهلين |
| MANAGER | «اختيار موظف آخر» مخفي تماماً، ويُعرض الموظف المسؤول الحالي للقراءة فقط مع «اعتماد الموظف» | يُرفض أي `propertyEmployeeUserId` لا يساوي منشئ العقار عندما يكون منشئه `EMPLOYEE`؛ وإلا **403** |

- إخفاء الزر في الواجهة إجراء دفاعي فقط؛ **الخادم هو المرجع**.
- `resolveEmployee` يظل يتحقق أن الموظف نشط وتابع للمدير، لذلك حتى الإسناد الصحيح لموظف فريق آخر يُرفض.
- لا يتم تعديل `Property.createdByUserId` أو أي إسناد دائم للعقار عند تسجيل الصفقة.
- إسناد موظف العميل (`clientEmployeeUserId`) وتوزيع العمولات لم يتغيرا.

سلوك مقصود: العقار المنشأ بواسطة OWNER/MANAGER ليس له موظف عقار، لذلك لا يستطيع المدير تسجيل صفقة عليه (403). هذا متسق مع «لا تجاوز للمدير».

## 4. قواعد اختيار العميل (الخطوة 2)

نفس `clientOwnershipWhere` المستخدم في `/clients` هو مصدر الحقيقة داخل استعلام قاعدة البيانات:

| الدور | ما يستطيع البحث عنه واختياره |
|---|---|
| OWNER | جميع عملاء الشركة المؤهلين (`Client` الفعلي) |
| MANAGER | عملاء المدير نفسه + عملاء موظفي فريقه الحاليين فقط |
| EMPLOYEE | لا يدخل المعالج أساساً (403 على مسارات الصفقات) |

- البحث على الخادم داخل **كل** النطاق المصرّح به، وليس أول صفحة محمّلة فقط.
- الحقول القابلة للبحث: الاسم والهاتف. الهاتف يُستخدم للمطابقة فقط ولا يُعاد في الاستجابة.
- الاستجابة محدودة بـ `id`, `name`, `responsibleUserId`, `responsibleEmployeeName` — لا هواتف ولا حقول خاصة.
- ترقيم مؤشر: `nextCursor` + جلب تدريجي عند التمرير، بحد أقصى 50 لكل صفحة من الواجهة.
- `ClientReview` المعلّق/المرفوض ليس صف `Client`، لذلك لا يظهر ولا يُقبل عند الإنشاء.
- التحقق النهائي عند `POST /deals`: `client.findFirst({ id, ...clientOwnershipWhere })` → عميل غير مصرّح أو غير موجود = **404** (بلا كشف وجود).
- اختيار العميل يُحدّث «ملخص الصفقة» فوراً، ويُحفظ `clientId` في مسودة المعالج ويُرسل كما هو.

### الواجهة

- تحميل عند فتح الخطوة 2، مع تأخير 250ms للبحث.
- «جارٍ التحميل...» أثناء الجلب، «جارٍ تحميل المزيد...» عند الترقيم.
- «لا يوجد عملاء متاحون» عند غياب النتائج بلا بحث، و«لا توجد نتائج» عند بحث بلا مطابقة.
- رسالة خطأ + زر «إعادة المحاولة» عند فشل الـ API.
- لا يمكن الانتقال للمراجعة بدون عميل مختار وموظف عميل معتمد.

تغطية اختبارات الصفقات (11 اختباراً):

1. OWNER يرى/يستخدم تجاوز موظف العقار، والصفقة تحفظ `propertyEmployee` المختار و`clientEmployee` الصحيح.
2. MANAGER لا يستطيع تجاوز موظف العقار → **403**.
3. MANAGER ينشئ صفقة مصرّحة لفريقه بنجاح.
4. `/deals/client-options` يعيد عملاء فعليين مصرّح لهم.
5. البحث يعمل عبر الصفحات (`limit=2` + `cursor`) ويجمع النتائج الثلاث كاملة.
6. المدير يرى عملاء فريقه وعملاءه الشخصيين.
7. المدير لا يرى عملاء فريق آخر؛ OWNER يراهم.
8. البحث بالهاتف يجد العميل الصحيح دون إرجاع الهاتف.
9. سجل `ClientReview` المعلّق لا يظهر في خيارات العملاء.
10. عميل فريق آخر عند الإنشاء → 404، وموظف فريق آخر → 403.
11. حفظ المبالغ والعمولات `1.234` و`0.001` بدقة، وإسناد الموظفين.

## 6. قيود متبقية

- قاعدة `arkan_crm` الحقيقية تحتوي حالياً على **0 `Client`**، لذا سيظهر «لا يوجد عملاء متاحون» حتى يُنشأ عميل فعلي. لم يتم إنشاء أو تعديل أي بيانات أعمال.
- `/deals/options` ما زال يعيد مصفوفة `clients` كصفحة أولية/احتياطية للتوافق؛ يمكن إزالتها لاحقاً بعد التأكد من عدم وجود مستهلكين آخرين.
- ترقيم المؤشر يعتمد على ترتيب `(name, id)`؛ الإدخال/التعديل المتزامن أثناء التصفح قد يغيّر موضع عنصر بين الصفحات (سلوك cursor معتاد، لا يؤثر على صحة التحديد).
- لم تُجرَ جولة نقر يدوية في المتصفح ضمن هذه المهمة؛ الأدلة هي اختبارات API فعلية + typecheck + lint. حالة الواجهة (تحميل/فراغ/خطأ) مبنية على الحالات المذكورة أعلاه.
- لا ترحيل قاعدة بيانات ولا تفعيل جديد مطلوب لهذه المهمة.
