# تدقيق الجاهزية قبل الإطلاق — Arkan CRM (≈20 مستخدمًا)

**التاريخ:** 2026-11-10  
**النطاق:** المراجعة الوظيفية والتشغيلية والأمنية قبل الاستخدام اليومي في شركة عقارية كويتية بحجم ~20 مستخدمًا.  
**النوع:** **تدقيق فقط** — لم يُعدَّل أي كود أو مخطط أو قاعدة بيانات.

**الحكم النهائي:** **CONDITIONAL GO** لإطلاق مضبوط داخل شبكة المكتب بعد إغلاق بنود P0 (أدناه). **NO-GO** كإطلاق إنتاجي عام/سحابي قبل تلك البنود.

---

## 0. ملخص تنفيذي

النواة اليومية للـCRM **مكتملة ومختبَرة بدرجة جيدة**: المصادقة والجلسات والصلاحيات، إدارة الموظفين والفرق والصلاحيات، دورة العقارات الكاملة (إنشاء/تعديل/اعتماد/رفض/طلب تعديل/إعادة إرسال/محذوفات/استعادة/حذف نهائي/صور/أكواد P-A/كشف التكرار)، العملاء والمراجعات والإسناد المسؤول، المتابعات والمزامنة والتذكيرات والسجل، الإشعارات (داخلية + Web Push)، لوحة المدير، والبحث/الفلترة/الترقيم.

لكن **الإطلاق الفعلي** يعيقه خمسة أمور رئيسية:

1. **لا توجد طريقة إنتاجية لإنشاء أول OWNER** (الـseed معطّل في الإنتاج، و`promote-owner.cjs` يرقّي مديرًا موجودًا فقط).
2. **لا يوجد نشر إنتاجي جاهز** (Compose يشغّل PostgreSQL/Redis فقط؛ لا خدمات تطبيق، لا TLS/Reverse Proxy، لا CI/CD، لا runbook تشغيل).
3. **النسخ الاحتياطي يدوي/غير مؤتمت** (يوجد نسخ موثّق ومُتحقَّق مرة واحدة، لكن لا جدولة/احتفاظ/خارج الموقع).
4. **صفحتا الصفقات والمالية تعملان ببيانات وهمية داخل الذاكرة** وموجودتان في التنقّل الأساسي — أي إدخال يضيع عند التحديث.
5. **إسناد الموظفين للعقارات غير منفّذ** (لا يوجد API لإنشاء `PropertyAssignment`)، وتبويب «المسندة إلي» يظهر دائمًا فارغًا.

## 3. البيانات والسلامة

### نقاط قوة مؤكدة

- معاملات Prisma في مسارات الإنشاء/التعديل/الاعتماد؛ الـtriggers/الـconstraints تمنع الحالات غير الصالحة.
- **تفاؤل التزامن** في العقارات: `version` يُفحص ويُزاد عند الاعتماد/الرفض (`Stale version` → 409).
- **مراجعات العملاء**: بصمة `base` تُقارن داخل نفس المعاملة قبل التطبيق (`CONFLICT` بدل الكتابة فوق تغيير أحدث).
- **منع التكرار/الطمأنينة**: قفل تكرار إرسال العميل، كشف تكرار العقارات مع advisory locks، مفاتيح event فريدة للإشعارات، و`@@unique` للدفعات.
- **حذف العقار النهائي**: يمنع الحذف عند وجود صفقات/مصروفات/اهتمامات، ينقل سجل المتابعة إلى تاريخ محفوظ (propertyId=null) ويحذف الصور من التخزين بعد commit.
- إعادة إسناد الموظف/تعطيل الحساب تُبطل الجلسات وتُحدّث النطاقات (اختبارات revocation).
- لا حذف للعملاء/الجهات = لا يتيم/فقدان سجلات مرتبطة.

### مخاطر بيانات

1. **إسناد العقارات غير المنفّذ** يعني أن مسؤولية متابعة العقار تُحسب من المُدخِل (`createdByUserId`) لا من موظف مُسند؛ إعادة الإسناد غير ممكنة من الواجهة.
2. **الصفقات/المالية الوهمية**: أي بيانات مالية تُدخل هناك غير محفوظة → خطر فقدان/قرارات خاطئة.
3. **العملاء بلا حذف/أرشفة**: بيانات خاطئة تبقى ظاهرة؛ يلزم إجراء يدوي في DB (غير موثّق).
4. **لا استيراد**: ترحيل دفتر العملاء/العقارات الحالي يدوي وعرضة للخطأ.
5. **لا سجل تدقيق مرئي** للمالك لمتابعة تغييرات الفريق.

## 4. تجربة الاستخدام (مراجعة كود فقط — بلا متصفح)

- التنقّل عربي RTL مع Shells منفصلة للمدير/الموظف، وحالات تحميل/فراغ/خطأ موجودة في صفحات العملاء والموظفين والعقارات (فحص كود).
- **خطأ UX مؤكد**: تبويب «المسندة إلي» في خصائص الموظف يظهر دائمًا فارغًا لأنه لا يوجد إسناد عقارات.
- **خطر UX مؤكد**: صفحة الصفقات أساسية في التنقّل وتقبل إدخالًا وهميًا (رغم وجود ملاحظة). يجب إخفاؤها أو تعطيل الحفظ الوهمي قبل الإطلاق.
- **لا تغيير لكلمة المرور**: المستخدم لا يستطيع تدوير كلمة مروره بنفسه؛ OWNER فقط يحددها عند الإنشاء.
- **لا استيراد/تصدير**: خطوات إدخال دفتر موجود طويلة.
- **غير متحقق**: الموبايل، لوحة المفاتيح، ARIA، التباين، RTL على المتصفحات الفعلية.

### النسخ الاحتياطي (موجود لكن غير مؤتمت)

- **نسخة موثّقة 2026-11-08** في `D:\ArkanBackups\owner-hierarchy-20261108-034605`: `pg_dump` + صور كاملة + SHA-256 لكل صورة + `pg_restore --list` + **استعادة ناجحة على قاعدة disposable** مع تطابق الأعداد و19 migration.
- **نسخة 2026-11-09** (`last-backup.txt`): DB dump فقط + SHA-256 — **بلا صور**.
- لا سكربت نسخ احتياطي في المستودع، ولا Scheduled Task خاص بالنسخ، ولا سياسة احتفاظ/خارج الموقع/دورية موثّقة.
- `RESTORE.txt` يوضح خطوات الاستعادة (DB + images) — جيد، لكنه يفترض إيقاف الخدمة و`dropdb/createdb` يدويًا.

**التقييم:** النسخ **قابل للاستعادة** (مُثبت مرة)، لكنه **غير مؤتمت/غير مجدول**، وآخر نسخة لا تشمل الصور.

### التشغيل

- `/health` و`/health/ready` (DB+Redis) يعملان.
- لا monitoring/metrics/alerting؛ السجلات نصية فقط.
- `backend.log` يبلغ 5.22MB بلا تدوير.
- scheduler المتابعات داخل العملية (setInterval كل 15 دقيقة) — مناسب لعملية واحدة، وقد يكرر الفحص مع تعدد النسخ (الإشعارات محمية بمفاتيح حدث).
- إعادة التشغيل: مدير التطوير `scripts/backend-dev.ps1` يعيد تشغيل watcher، لكنه أداة تطوير وليس خدمة إنتاج (لا systemd/NSSM/Docker restart policy).

### التكرار/انقطاع الشبكة

- منع التكرار موجود في العميل (قفل إرسال) والعقارات (idempotency/unique)، والمتابعات (batch idempotent)، والمراجعات (base freshness). الاختبارات تغطيها.

## 6. جاهزية النشر

| العنصر | الحالة |
|---|---|
| Dockerfiles | موجودة (backend يبني Nest، frontend standalone) |
| Compose | **PostgreSQL + Redis فقط**؛ لا خدمات backend/frontend، لا proxy/TLS |
| HTTPS/الكوكيز | الكود **يفشل بإغلاق** في الإنتاج إذا لم تكن `COOKIE_SECURE=true` والأصول HTTPS → يتطلب TLS فعليًا |
| الأسرار | `.env` محلي بأسرار تطوير؛ التحقق من المفاتيح قوي؛ لا Secret Manager |
| Migrations | `prisma migrate deploy` موجود؛ لا خطوة آلية في صورة/نشر |
| أول OWNER | **لا مسار إنتاجي**: seed معطّل في الإنتاج، و`promote-owner.cjs` يرقّي MANAGER موجودًا فقط |
| التخزين | مجلد محلي افتراضي `~/.arkan-crm/storage`؛ لا volume في Compose التطبيقي |
| الصحة/إعادة التشغيل | health endpoints جيدة؛ لا restart policy/خدمة نظام |
| CI/CD | غير موجود |
| CSP | **Report-Only** محليًا؛ قرار فرض الإنتاج غير محسوم |
| Web Push | VAPID مضبوط محليًا؛ يتطلب HTTPS ومفاتيح إنتاج |
| نسخ احتياطي آلي | غير موجود |
| التوثيق | **قديم/متضارب**: README وPROJECT_CONTEXT يصفان حالة أولية (واجهات وهمية، sessionStorage، بلا rate limiting) بينما الكود الحالي مختلف تمامًا؛ ومنافذ 3000/4000 مقابل 3001/4001 |
