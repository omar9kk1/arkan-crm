# تفاصيل الصفقة: أزرار دفع عمولة الموظفين للمالك

**التاريخ:** 2026-11-11
**النطاق:** زر «دفع العمولة» لكل بطاقة عمولة موظف داخل درج تفاصيل الصفقة، مع إعادة استخدام Finance وإشعار الموظف.
**الحالة:** مكتمل، بدون ترحيل قاعدة بيانات وبدون أي دفع حقيقي أو تعديل بيانات أعمال.

## 2. إعادة استخدام Finance

- الزر يستدعي نفس النقطة الموجودة: `POST /finance/commissions/:id/pay` عبر `confirmCommissionPayout()` في `lib/api/finance-api.ts` (لم تُنشأ نقطة دفع جديدة).
- الخادم يبقى OWNER-only (`@Roles(Role.OWNER)` + `assertOwner`)، ويضبط `status=PAID`, `paidAt`, `paidById` ويحدّث حركة دفتر Finance نفسها (لا يكرّرها).
- التحقق من التكرار قائم على `updateMany({ status: PENDING })` داخل معاملة، مع مسار idempotent للعمولة المدفوعة مسبقاً.
- المبالغ تُعرض كما هي من الـ API بثلاث خانات عشرية (مثال `100.000 د.ك`) دون تحويل إلى float.

## 3. الإشعار

- يُنشأ داخل نفس معاملة تأكيد الدفع بعد نجاح claim الحالة، لذلك لا يوجد دفع بلا إشعار أو إشعار بلا دفع.
- المستلم هو `Commission.employee.userId` فقط.
- العنوان: «صرف عمولة»، والنص: «تم صرف عمولتك عن العقار {A-code/reference} بقيمة {amount} د.ك.»
- `eventKey = COMMISSION_PAID:<commissionId>` مع فهرس `(userId, eventKey)` الفريد: retry أو طلب متزامن على عمولة مدفوعة لا يمر بمسار الإنشاء أصلاً، والفهرس يمنع أي تكرار إضافي.
- النوع المستخدم `SYSTEM` لتجنّب ترحيل enum جديد؛ لا تغيير على مخطط قاعدة البيانات.

## 4. السلوك في الواجهة

| الحالة | OWNER | MANAGER |
|---|---|---|
| عمولة `PENDING` | شارة «بانتظار الدفع» + زر «دفع العمولة» | شارة «بانتظار الدفع» فقط |
| تأكيد الدفع | بطاقة تأكيد داخلية: اسم الموظف، رمز العقار، المبلغ الدقيق، «تأكيد الدفع»/«إلغاء» | لا شيء |
| عمولة `PAID` | «تم الدفع · YYYY-MM-DD» بلا زر | نفس الحالة للقراءة فقط |
| أثناء الطلب | تعطيل الأزرار ومنع الإرسال المكرر | — |
| فشل الطلب | رسالة خطأ داخل البطاقة وبقاء الحالة دون تغيير | — |

- العمولات مستقلة: دفع عمولة موظف العقار لا يمس عمولة موظف العميل.
- بعد النجاح يُعاد جلب `GET /deals/:id` وتحديث الدرج والقائمة، فيتحول الزر إلى «تم الدفع».
- بطاقة عمولة الشركة بلا أي زر دفع.

## 5. الصلاحيات

- OWNER فقط يرى زر الدفع ويستطيع استدعاء نقطة الدفع.
- MANAGER يرى حالة الدفع للصفقات المصرّح بها فقط، وأي محاولة دفع مباشرة ترجع **403** (مغطاة في اختبارات Finance القائمة).
- لا تُكشف بيانات Finance أخرى ولا صفقات فرق أخرى.

## 6. نتائج الاختبارات

بيئة الكتابة: `arkan_crm_api_test` فقط، دون أي دفع حقيقي.

| الأمر | النتيجة |
|---|---|
| `npm run test -w @arkan/backend -- test/finance.spec.ts test/deals.spec.ts test/frontend-deal-model.spec.ts` | **22/22 نجحت** (3 suites) |
| `npm run typecheck -w @arkan/backend` | 0 |
| `npm run typecheck -w @arkan/frontend` | 0 |
| ESLint على الملفات المتأثرة | 0 |

تغطية الاختبارات:

1. دفع عمولة واحدة فقط (`0.005`) وترك الأخرى `PENDING`.
2. `PAID` مع `paidAt` و`paidById` الصحيحين.
3. حركة Finance واحدة لكل عمولة، ولا تكرار عند retry أو الطلبات المتزامنة.
4. إشعار واحد للموظف الصحيح يحتوي رمز العقار والمبلغ `0.005` و«د.ك»، ولا يتكرر عند retry.
5. إشعار مستقل للعمولة الثانية عند دفعها.
6. تفاصيل الصفقة تعيد معرّفات العمولات وحالاتها الصحيحة (`PAID/PENDING`).
7. MANAGER/EMPLOYEE على نقطة الدفع → 403 (اختبار Finance القائم).
8. عدم تغيّر مبالغ الصفقة أو توزيع العمولات أو حالة العقار.
9. اختبارات Deals السابقة (البحث، الصلاحيات، التزامن، الدقة) بقيت ناجحة.

## 7. قيود متبقية

- نوع الإشعار `SYSTEM` بدل نوع مخصص `COMMISSION_PAID`؛ إضافة قيمة enum تتطلب ترحيل قاعدة بيانات وموافقة منفصلة.
- لا توجد اختبارات UI آلية (لا مكتبة DOM)؛ تم التحقق من ظهور الزر للمالك فقط عبر فحص الشيفرة وtypecheck/lint، دون جولة نقر يدوية في المتصفح.
- العملة المعروضة «د.ك» لأن عمولات الصفقات KWD فقط في الخادم.
- لا ترحيل قاعدة بيانات ولا تفعيل مطلوب.
