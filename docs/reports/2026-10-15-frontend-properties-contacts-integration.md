## 1. الملخص التنفيذي ونطاق المرحلة

ربطت هذه المرحلة كل شاشات العقارات وجهات التواصل المعتمدة بواجهات الخلفية الحقيقية، **دون تغيير الشكل المُعتمد**. التغييرات في الملفات **الداخلية فقط**: الأحداث (`handlers`) وخطافات (`hooks`) والمحوّلات (`adapters`) والتحقق والإشارات (`API calls`).

**ما تم إنجازه فعليًا:**

1. أساس API مكتوب بأمانة الأنواع: `lib/api-client.ts` + `lib/api/{authorized,property-types,properties-api,contacts-api}.ts` + `features/auth/session.ts`.
2. محوّل صافٍ `lib/property-adapter.ts` يحول نموذج المعالج ثلاثي الخطوات إلى حمولات الخلفية، ويحوّل DTOs إلى نماذج العرض.
3. سجل جهات التواصل تحول بالكامل إلى `GET/POST/PATCH /contacts` (`lib/contact-registry.ts`).
4. المعالج ثلاثي الخطوات (`new-property-modal-v2.tsx`) يرسل `FormData` متعدد الأجزاء مع **صورة واحدة إلزامية**.
5. قوائم الموظف والمدير تعتمد على الخادم مصدرًا للحقيقة مع حالات التحميل/الفراغ/الخطأ والترقيم.
6. الصور تُجلب عبر `GET /properties/:id/image` بـ `Authorization` ثم تتحول إلى object URL يُحرَّر عند التغيير.
7. سير عمل المدير (اعتماد/رفض بسبب إلزامي + `version` + 409) وسير عمل الموظف (تصحيح `PATCH` ثم `POST /resubmit`) مربوطان.

**ما تبقّى خارج النطاق عمديًا:** تعديل العقارات المتاحة (`PropertyRevision`)، استبدال صورة عقار عند التعديل، ونقطة نهاية `CHANGES_REQUESTED` منفصلة (القسم 13).

## 4. طبقة عميل الـ API وإعادة استخدام الجلسة

- **لا بادئة `/api`:** المسارات نسبية (`/properties`, `/contacts`) وتُدمج مع `NEXT_PUBLIC_API_URL` عبر `new URL(path, baseUrl)`.
- **تفكيك الظرف `{ data }`:** `readJsonEnvelope` يعيد `parsed.data` فقط؛ غياب الظرف أو نص غير JSON يُفكَّك كخطأ بدل عرض بيانات وهمية.
- **المصادقة:** التوكن يُرسل في ترويسة `Authorization: Bearer` فقط — **أبدًا** في سلسلة الاستعلام أو `src` صورة.
- **التحديث عند 401:** `authorizedRequest` يستدعي `refreshAccessToken()` (single-flight عبر `session.ts`) ويعيد المحاولة **مرة واحدة فقط**؛ إن فشل التحديث تُمسح الجلسة ويُبث `SESSION_EXPIRED_EVENT` ليطهّر `AuthProvider` الحالة ويعرض رسالة انتهاء الجلسة العربية.
- **لغة المحتوى المُلتزم بها:** `FormData` يضبط `Content-Type` والمُحدِّد الحدود تلقائيًا (لا يُضبط يدويًا أبدًا)، ورؤوس JSON فقط تأخذ `Content-Type: application/json`.
- **لا تسجيل للتوكنات/كلمات المرور:** لا `console.log` للتوكن في أي مسار ناجح أو فاشل.
- **مهلة موحّدة:** 30 ثانية لكل الطلبات، وتُلغى عبر `AbortController` في `finally`.

**خريطة الأخطاء (`api-client.ts`):** `ApiError` يحمل `status` و`messages[]` الخام (إنجليزية) و`message` المُعرَّب عبر `displayMessage`:

| الحالة | النص المعروض |
| --- | --- |
| 409 | «تغيّر هذا العقار أو تمت مراجعته بالفعل. حدّث الصفحة لعرض أحدث حالته.» (مطابق حرفيًا لمتطلب المرحلة) |
| 401 | «البريد الإلكتروني أو كلمة المرور غير صحيحة، أو انتهت الجلسة.» |
| 403 | «ليس لديك صلاحية الوصول.» |
| 404 | «السجل غير موجود أو ليس لديك صلاحية لعرضه.» |
| 413 | خريطة رسائل الحجم، وإلا «حجم الصورة يتجاوز الحد المسموح به (5 ميجابايت).» |
| تحقق (400) | خريطة رسائل معروفة (منها «القيمة يجب أن تكون رقمًا غير سالب بكسر عشري من خانتين كحد أقصى.») وإلا النص الخام مُعرَّبًا مقاطعًا |
| شبكة/5xx | «تعذر الاتصال بالخادم…» / «تعذر إتمام الطلب. حاول مرة أخرى.» |

> **قرار توثيقي:** لا يُقدَّم fallback وهمي بأي حال؛ أي رسالة غير معروفة تظهر كما أرجعها الخادم حتى لا يُخفى سبب الفشل الحقيقي.

## 5. تكامل معالج الإضافة ثلاثي الخطوات

البنية **ثلاث خطوات بالضبط** — لا خطوة رابعة، لا حقل مطلوب جديد، لا صورة ثانية، لا جهة تواصل ثانية:

1. **الخطوة 1:** نوع الصفقة (`SALE`/`RENT`/`EXCHANGE`) + طريقة الإدخال (يدوي / لصق واتساب). تحليل الواتساب يبقى **محليًا** في المتصفح، والنص الملصوق **لا يُرسَل أبدًا** كوصف عام.
2. **الخطوة 2:** المحافظة/الحوض/الحارة/رقم القطعة/المساحة/الطوابق/السعر/التفاوض + **صورة واحدة إلزامية** بالضبط.
3. **الخطوة 3:** اختيار `OWNER`/`BROKER` موجود أو إنشاء واحد بـ الاسم + الهاتف، ثم المعاينة ثم الإرسال.

**سلوك الإرسال:**

- `createProperty(payload, imageFile)` يبني `FormData` حقيقيًا: سلسلة `payload` JSON + حقل `image` بالـ `File` الفعلي (لا رابط، لا نص وصفي).
- الحقول المالية/المساحات تُرسَل **كنصوص عشرية** (`'250000'`, `'400'`)، والحقول الاختيارية الفارغة **تُحذف** لا تُرسل كـ `''`.
- **أبدًا** `contactId` و`newContact` معًا: يُرسَل أحدهما فقط (يتحقّق منه الخادم أيضًا بـ 400).
- تُرسَل الصورة الفعلية `File`، والحقول المالية/المساحات نصوصًا عشرية، والأجولة (`floors`) تتحول إلى سجلات `FloorType` دون فقد تفاصيل الطوابق (`mapFloors` يدمج الأعلام `hasBasement`/`hasHalfFloor`/`hasQuarterFloor` في سجلات `BASEMENT`/`HALF`/`QUARTER` ويدمج النصوص بفاصلة « | »).
- **ردع إرسال مزدوج:** `submitting` حالة + `inFlight` ref يمنع التنفيذ المتزامن، وزر الإرسال معطّل ومُعلَّم أثناء الإرسال.
- **عند الفشل:** تبقى النافذة مفتوحة والقيم محفوظة، ويُعرض الخطأ المُعرَّب.
- **عند النجاح المؤكَّد فقط:** تُغلق وتُصفّر الحالة، ثم تُحدَّث القائمة.
- **التصحيح (`REJECTED`):** يُنفَّذ `PATCH` أولًا، ثم `POST /resubmit` **فقط** إن بقيت الحالة `REJECTED` بعد `PATCH`. إن نجح `PATCH` وفشل `resubmit` تُحدَّث القائمة بالصف المُصحَّح مع رسالة توضيحية وتبقى النافذة مفتوحة.

> **ملاحظة نموذجية:** `toCreatePropertyPayload` **لا يرسل `address`** — العنوان يُبنى من قطعة/حوض/حوض على العميل للعرض. هذه هي العادة الحالية القائمة وليست تغييرًا في التصميم.

## 6. تكامل جهات التواصل وحدود العملاء/المتابعات

- **السجل لم يعد في الذاكرة:** `useRegistryContacts`/`useVisibleContacts` تعتمد على `GET /contacts` (مع `refresh()` بعد الإنشاء).
- **التمييز عبر `Contact.type`:** `OWNER` و`BROKER` مُميّزان بمُعاملات تصفية منفصلة على الخادم.
- **`Contact.id` مستقر** ويُستخدم كمفتاح قائمة ومفتاح تحرير.
- **لا تعديل لسجلات العملاء (`Clients`) أو المتابعات:** لم يُمسَّ أي مكوّن `employee-clients` أو سجل متابعة.

> **تحققت فعليًا:** `grep` على `addRegistryContact|registryOwnerFields|registerPropertyContact|toPropertyFromNewV2` → **لا نتائج** (لا بقايا لاستدعاءات السجل القديم).

## 7. تكامل قوائم العقارات

- **الخادم مصدر الحقيقة:** `GET /properties` مع `status`/`listingType`/`limit`/`cursor`.
- **حالات العرض:** تحميل (هيكل تحميل)، فراغ (رسالة عربية)، خطأ (رسالة + إعادة محاولة).
- **حماية من الاستجابة القديمة:** عدّاد `requestId` تصاعدي في صفحة الموظف يمنع أن تتجاوز استجابة أقدم استجابة أحدث.
- **الترقيم حسب الاستجابة الفعلية:** `{ items, nextCursor }` مع زر «تحميل المزيد» (حدّ أقصى 3 صفحات × 100 ثم زر يدوي).
- **إعادة الجلب بعد كل تعديل:** بعد الإنشاء/الاعتماد/الرفض/التصحيح تُستدعى `listProperties` من جديد.
- **البيانات تنجو من إعادة التحميل:** تجربت فعليًا بإعادة قراءة القائمة بعد الإنشاء في اختبار العقد.
- **التصميم الحالي محفوظ:** كروت الموظف والمدير ودرج التفاصيل محفوظة شكلًا؛ التغييرات البصرية الوحيدة حالات التحميل/الخطأ/الفراغ.

## 8. تكامل الصور المؤمَّنة

- **الجلب:** `GET /properties/:id/image` عبر `authorizedRequest` → `Blob` → `URL.createObjectURL`.
- **تحرير الـ object URL:** في دالة التنظيف (`cleanup`) عند فك التركيب أو تغيّر `propertyId`، مع إلغاء التفعيل (`active` flag) لمنع استجابة متأخرة من الفوز على أحدث استجابة.
- **لا توكن في العنوان أبدًا:** التوكن في الترويسة فقط، لذا لا يمكن أن تتسرب عبر `src` أو سلسلة استعلام.
- **لا تخزين دائم للـ blobs الخاصة:** كل مستهلك يجلب ويحرّر؛ لا ذاكرة مشتركة دائمة.
- **تحميل عند الظهور فقط:** `useInViewport` (IntersectionObserver بهامش `rootMargin: 300px`) يفتح الطلب — القوائم الطويلة **لا** تطلق طلب صورة لكل صف عند التركيب. هذا هو السلوك المعتمد الحالي ويُوثَّق هنا كفارق تنفيذي عن «طلب فوري».
- **لا كشف مسار تخزين:** الواجهة لا تعرض `storagePath` ولا أي مسار ملف.
- **التصميم والـ alt وحالة التحميل محفوظة** على الكروت.

## 9. سير عمل المدير

- **عرض `PENDING`:** تبويب «بانتظار الموافقة» مبني على `status=PENDING` من الخادم.
- **عرض جهة التواصل الخاصة المصرَّح بها:** `PrivatePropertyDto.contact` فقط حين يُعيده الخادم؛ لا طلب إضافي لاستعادة بيانات مخفية.
- **الاعتماد:** `POST /properties/:id/approve` مع `{ version }` الحالي.
- **الرفض بسبب إلزامي:** `review-action-dialog.tsx` يرفض إرسال سبب فارغ/من مسافات (يتحقّق الخادم أيضًا بـ 400).
- **حالة مستندة إلى الخادم:** لا حالة متفائلة (optimistic) — تُقرأ الحالة من استجابة القرار ثم تُعاد القائمة.
- **منع النقر المزدوج:** `busyId` يعطّل زر الصف أثناء تنفيذ القرار.
- **رسالة 409 المطلوبة:** نصّان مطابقان حرفيًا (القسم 4) يُعرضان ثم تُعاد القائمة لعرض أحدث حالة.
- **النقرات غير المصدَّقة:** الرفض والاعتماد يُرفضان بـ 403 لرمز الموظف (مُختبَر).

> **عدم تبديل الأدوار:** الموظف لا يرى أزرار المدير ولا يستطيع استدعائها.

## 10. سير عمل الموظف

- **`PENDING`/`REJECTED` الخاصة فقط:** يرى صفوفه فقط؛ أي صف لموظف آخر يرجع 404 (مُختبَر) ويختفي من القائمة (مُختبَر).
- **سبب الرفض:** `reviewNotes` تظهر لصاحب العقار فقط (مُختبَر: تحوي نص الرفض).
- **التصحيح عبر `PATCH`:** يحمل `version` الحالي؛ نسخة قديمة ترجع 409 بالنص المطلوب (مُختبَر).
- **إعادة الإرسال عبر `POST /properties/:id/resubmit`:** **وحدها** تنقل إلى `PENDING`؛ الإصلاح وحده **لا** ينشر (مُختبَر: بعد `PATCH` بقيت الحالة `REJECTED` ثم `resubmit` ← `PENDING`).
- **صاحب العقار وحده يصحح/يعيد الإرسال:** رمز موظف آخر يرجع 403 (مُختبَر).
- **لا تعديل لأي عقار `AVAILABLE`:** `deriveMine` يمنع التحرير خارج `PENDING`/`REJECTED` لموظف، و`updateProperty` غير متاح للمدير أو لغير المالك.

> **بديل صورة التصحيح:** `PATCH` لا يقبل حقل صورة، لذا يتعامل المعالج مع صورة العقار المخزنة كأ满足 لخطوة 2 عند التحرير؛ اختيار صورة جديدة يعرض تنبيهًا صريحًا بأن الاستبدال غير مدعوم في هذه المرحلة.

## 11. الخصوصية في الواجهة والتفويض الخلفي

- **الخادم هو المرجع:** `lib/property-privacy.ts` لا يبني قراراته من بيانات مخفية بل من **وجود** `contact` في الاستجابة نفسها (`canViewPropertyContact(property)` بمعيار واحد).
- **الدوال المعتمدة على `AuthUser {id, role}`** لا تفترض صلاحية من الحالة المحلية.
- **لا طلب إضافي لبيانات مخفية:** لا توجد أي استدعاء تفويض أو `contactId` منفصل لاستعادة اسم/هاتف صاحب عقار `AVAILABLE` لغير مالكه.
- **تفريغ الحالة الخاصة عند الخروج:** `signOut()` يمسح `sessionStorage`/`localStorage` و`AuthProvider` يصفّر `user`، ويُبث `SESSION_EXPIRED_EVENT` عند انتهاء الجلسة ليُخزَّن التنبيه ويطهر الحالة.

- **الـ DTOs مكشوفة للنماذج فقط:** `property-types.ts` يصرّح بأن الخاصيات الخاصة موجودة على `PrivatePropertyDto` فقط.
