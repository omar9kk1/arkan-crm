### الأداة

نفس harness السابق (`scripts/load-test/keepalive-compare.cjs`):
- keep-alive agent بـ`maxSockets=128`، `timeout=20s`.
- نفس خليط الطلبات ونفس توزيع الأدوار (owner/manager×2/employee).
- `level × 4` طلبًا: 50 → 200 طلب، 100 → 400 طلب.
- `/health` عبر agent منفصل كل 500 ms.
- أُضيف للـharness (أداة فقط): `LOAD_LEVEL` وإحصاءات لكل endpoint و`freeMb` — دون تغيير أي إعداد اتصال أو خليط.
- event-loop أُخذ عبر Inspector (`monitorEventLoopDelay`, resolution 20ms) خلال نافذة التشغيل.

**فرضية غير مؤكدة (لا تُقدَّم كحقيقة):** الفارق المتبقي ~9% مقابل 91 RPS يُرجَّح أنه بيئي: حمل CPU خلفي 12–31%، مشروع آخر يشغّل Vitest، وتشغيل Next/Nest dev. لا تتوفر قياسات ظروف مطابقة لخط الأساس Task 16، لذلك **لا يمكن الجزم** بوجود تراجع أو بتحسن full-mix.

## 4. التحقق من أن التحسين ما زال فعالًا

- **عدد الاستعلامات** (قياس مؤقت بـPrisma query events، 50 طلبًا متتاليًا):
  - MANAGER: **7.20 استعلامًا/طلب** (بدل 11.14).
  - EMPLOYEE: **10.04 استعلامًا/طلب** (بدل 15.32).
- **زمن SQL لكل طلب**: MANAGER **29.6 ms** (بدل 42.4)، EMPLOYEE **61.9 ms** (بدل 154.0).
- **حجم الاستجابة**: 31,259 B (manager) و30,737 B (employee) — بلا تغيير.
- **العقد**: لم يتغير أي كود منذ Task 17؛ التحقق الحقل بحقل هناك (193 بطاقة، 0 اختلاف) ما زال ساريًا.
- **فحوص مركزة الآن**: `followups-pagination` + `followup-history-authorization` → **2 suites / 12 اختبارًا ناجحًا** (ترقيم >1,000، عزل، 404 لسجل الفرق).
- **55-check harness**: نُفّذ في Task 17 (55/55) ولم يُعد تشغيله هنا لأنه يتضمن حمل 100 إضافي؛ لا تغييرات كود منذ ذلك الحين.

## 6. أبرز الاختناقات المتبقية (بالقياس)

1. **`/follow-ups?limit=50`** أعلى P50 بين endpoints (3,899 ms) في دفعة 400 طلب؛ يليه `/employees` (3,525) وفرزه (3,427). هذه أزمنة queueing تحت الحمل وليست زمن SQL.
2. **حارس الجلسة**: استعلامان لكل طلب على كل المسارات (`RefreshToken` + `User`).
3. **fingerprint مزامنة الموظف**: 5 استعلامات لكل أول صفحة (10.04 إجمالًا) — أكبر بند متبقٍ في مسار المتابعة.
4. **summary + cards**: استعلامان بعد تحسين Task 16/17.

**التوصية التالية:** توحيد fingerprint نطاق الموظف في استعلام SQL واحد (أو دفعه في اتصال واحد) ثم إعادة baseline كامل على مضيف هادئ. لا يُنصح بأي تعديل آخر قبل قياس معزول.
