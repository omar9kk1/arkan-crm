# معالج الصفقات: تأكيد الموظف تلقائياً للمدير

**التاريخ:** 2026-11-11
**النطاق:** الخطوة 1 «اختيار العقار» والخطوة 2 «اختيار العميل» — إزالة «اعتماد الموظف» عن المدير مع تأكيد تلقائي.
**الحالة:** مكتمل، بدون ترحيل قاعدة بيانات وبدون تغيير أي بيانات أعمال حقيقية.

## 2. كيف يعمل التأكيد التلقائي

الدالة النقية:

```ts
isEmployeeAttributionConfirmed({
  isOwner,
  manuallyConfirmed,
  responsibleUserId,
  attributedUserId,
  eligibleUserIds,
})
```

- **OWNER:** تعيد `manuallyConfirmed` فقط — نفس مسار «اعتماد الموظف» اليدوي دون أي تغيير.
- **MANAGER:** تعيد `true` فقط إذا تحققت الشروط الثلاثة:
  1. يوجد موظف مسؤول فعلي (`responsibleUserId`).
  2. هذا الموظف ضمن `employees` المؤهلين العائدين من `/deals/options` (نشط، دوره `EMPLOYEE`، وضمن فريق المدير).
  3. `attributedUserId` في المسودة يطابق الموظف المسؤول الفعلي.

أي مسودة قديمة تحتوي موظفاً مختلفاً، أو عقار/عميل بلا موظف مسؤول، أو موظف غير مؤهل → تبقى غير مؤكدة ويُمنع الانتقال برسالة عربية واضحة.

### المزامنة وإعادة الضبط

- عند تغيير العقار أو العميل تُعاد تهيئة حقول الموظف من العنصر المختار، وتُصفَّر علامة التأكيد اليدوي (`setConfirmed`).
- تأثيرا مزامنة للمدير يثبّتان `propertyEmployeeUserId/Name` و`clientEmployeeUserId/Name` على الموظف المسؤول الفعلي حتى مع مسودة محفوظة، فلا يبقى تجاوز قديم.
- التأكيد المشتق يُحسب في كل تصيير، لذلك ينتقل المدير بـ«التالي» مباشرة بعد اختيار العقار/العميل، ويبقى صحيحاً عند الرجوع/المتابعة.

### التحقق

| المرحلة | المدير | المالك |
|---|---|---|
| الخطوة 1 | يمنع بلا عقار، أو بلا موظف مسؤول، أو بموظف غير مؤهل | يمنع بلا عقار أو بلا اختيار/اعتماد يدوي |
| الخطوة 2 | يمنع بلا عميل، أو بلا موظف مسؤول، أو بموظف غير مؤهل | يمنع بلا عميل أو بلا اختيار/اعتماد يدوي |
| الخطوة 3 | إعادة تحقق من العقار/العميل والتأكيد الفعلي قبل الإرسال | إعادة تحقق من التأكيد اليدوي قبل الإرسال |

الحقول المرسلة في `POST /deals` هي نفس `draft.propertyEmployeeUserId` و`draft.clientEmployeeUserId` بعد المزامنة.

## 3. سلوك الواجهة

| العنصر | MANAGER | OWNER |
|---|---|---|
| اسم الموظف المسؤول | ظاهر للقراءة فقط | ظاهر |
| «اختيار موظف آخر» | مخفي في الخطوتين | ظاهر وفعّال |
| «اعتماد الموظف» | مخفي في الخطوتين | ظاهر وفعّال |
| حاوية الأزرار | لا تُصيَّر (لا مساحة فارغة) | كما هي |
| «التالي» | يعمل تلقائياً بعد الاختيار | يتطلب الاعتماد اليدوي كما كان |

«ملخص الصفقة» يعرض اسم موظف العقار/العميل فور اكتمال التأكيد الفعلي، ويظهر «بانتظار الاعتماد» فقط في مسار المالك قبل الاعتماد.

## 4. الأمان (بدون تغيير)

- الخادم ما زال يفرض: المدير لا يجاوز `propertyEmployeeUserId` ولا `clientEmployeeUserId`، وأي تجاوز مغاير → **403**.
- المالك يحتفظ بصلاحية التجاوز.
- التحقق من العميل يتم عبر `clientOwnershipWhere` (404 لغير المصرّح)، ومن الموظف عبر `resolveEmployee` (نشط + دوره + فريقه).
- لا يتم تعديل `Property.createdByUserId` أو `Client.responsibleEmployeeId` عند إنشاء الصفقة، والعمولات ودقة KWD كما هي.

اختبارات الوحدة الجديدة:

- المدير مؤكد تلقائياً عندما تطابق المسودة الموظف المسؤول المؤهل.
- مسودة قديمة تشير إلى موظف آخر (حتى لو مؤهل) تبقى غير مؤكدة.
- موظف مسؤول مفقود أو غير مؤهل لا يُعتمد أبداً.
- المالك يعتمد فقط على التأكيد اليدوي، ويستطيع اعتماد موظف مختلف (تجاوز).

اختبارات الصفقات السابقة (12) بقيت ناجحة: إنشاء الصفقة، تجاوز موظف العقار/العميل و403، البحث والترقيم، عزل الفرق، دقة المبالغ، التزامن، وثبات الإسناد الدائم.

## 6. قيود متبقية

- لا توجد اختبارات UI آلية (لا مكتبة DOM في المستودع)؛ تم التحقق من ظهور/إخفاء الأزرار عبر تمرير `showConfirm={isOwner}` و`allowOverride={isOwner}` في الخطوتين، مع typecheck وlint، ولم تُجرَ جولة نقر يدوية في المتصفح.
- إذا كان العقار/العميل بلا موظف مسؤول مؤهل، يمنع المعالج المتابعة للمدير برسالة واضحة بدل اختلاق موظف. المالك يستطيع الإسناد يدوياً ضمن صلاحية التجاوز.
- مسودة محفوظة تشير إلى عميل خارج الصفحة الأولى من خيارات العملاء تحتاج إعادة اختياره من البحث (سلوك سابق، لا علاقة له بهذا التغيير).
- لا ترحيل قاعدة بيانات ولا تفعيل مطلوب.
