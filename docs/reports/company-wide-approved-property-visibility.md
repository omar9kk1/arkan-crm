# رؤية العقارات المعتمدة على مستوى الشركة

**التاريخ:** 2026-11-11  
**المشروع:** `D:\Projects\arkan-crm`  
**النطاق:** إتاحة العقارات المعتمدة (`AVAILABLE`) لكل موظفي/مديري الشركة مع الحفاظ على خصوصية بيانات المالك/جهة الاتصال وصلاحيات الإدارة.  
**الحالة:** مكتمل.

---

## 1. السبب المؤكد

كانت `propertyVisibilityWhere` تعيد للمدير:

```ts
OR: [
  { createdByUserId: viewer.id },
  { createdByUser: { employee: { managerUserId: viewer.id } } },
]
```

أي عقارات المدير وفريقه فقط. لذلك لم يكن المدير يرى العقارات المعتمدة التي أنشأتها فرق أخرى.

كما أن `serializeProperty` كان يسمح لأي مدير بالمرور إلى `PrivatePropertyDto`، وكان يعرض `reviewNotes` و`proposedOwner` قبل فحص نطاق الفريق. توسيع الرؤية دون إصلاح ذلك كان سيسبب تسريب بيانات خاصة.

---

## 2. تغييرات الرؤية

### قبل/بعد

| الدور | قبل | بعد |
|---|---|---|
| OWNER | كل غير المحذوف | كما هو |
| MANAGER | عقاراته + فريقه فقط | **كل `AVAILABLE` معتمد** + عقاراته + فريقه (بما فيها PENDING/REJECTED الخاصة به) |
| EMPLOYEE | كل `AVAILABLE` + طلباته PENDING/REJECTED | كما هو |

- `PENDING` و`REJECTED` لفرق أخرى **لا تظهر** للمدير.
- `PENDING` و`REJECTED` لموظف آخر **لا تظهر** للموظف.
- `deletedAt != null` (Trash) مخفي عن كل مسارات القراءة العادية.
- فقط `AVAILABLE` هي الكتالوج المعتمد المشترك. لم تُغيَّر حالات `SOLD/RENTED/ARCHIVED` أو انتقالاتها؛ تبويب «العقارات» الحالي يعرض `AVAILABLE` فقط.

## 3. الخصوصية على مستوى الحقول

`serializeProperty` يعيد الآن **PublicPropertyDto** فقط للمدير من خارج فريق منشئ العقار، حتى لو كان العقار معتمدًا ومتاحًا.

### بيانات عامة مسموحة

- الكود/المرجع والعنوان.
- المحافظة/المنطقة/البلوك/القطعة/العنوان.
- المساحة، الطوابق، السعر، نوع العرض، الوصف.
- الصورة المعتمدة.
- الحالة والتوافر.
- اسم الموظف المسؤول (`responsibleName`) ودوره.
- `isMine` الخاص بالمشاهد.

### بيانات خاصة لا تظهر لغير المخوّل

- `contact` و`contactId`.
- اسم/هاتف المالك أو الوسيط.
- `proposedOwner`.
- `reviewNotes`.
- `duplicateCandidateIds`.
- أي raw approval rows أو storage keys.

### من يحصل على البيانات الخاصة؟

- OWNER.
- منشئ العقار (إن كان يملك جهة الاتصال).
- مدير منشئ العقار داخل فريقه الحالي.
- صفوف أنشأها OWNER تبقى ضمن نطاق الإدارة القائم.

`GET /properties`, `GET /properties/:id`, الصور، البحث، والاستجابة المباشرة كلها تمر عبر نفس المحوّل؛ لا يوجد إخفاء في React فقط.

## 4. البحث والفلترة والمطابقة

- `GET /properties` يستخدم `propertyVisibilityWhere` قبل أي بحث/فلتر.
- البحث `q` يشمل كود A/P، العنوان، الحي، المحافظة، والمساحة.
- `status` و`listingType` و`governorate` و`district` تعمل فوق نفس النطاق.
- Cursor pagination كما هو، دون تكرار الصفوف (Prisma OR واحد).
- `openImage` يستخدم نفس النطاق، فالمدير/الموظف من فريق آخر يستطيع عرض صورة العقار المعتمد.
- `assertInterestValid` و`upsertInterests` في مراجعات/عملاء المطابقة يستخدمان نفس `propertyVisibilityWhere`، لذلك عقار الفريق الآخر المعتمد صالح للمطابقة.
- لا تغيير في منطق duplicate detection أو property assignment.

---

## 5. الصلاحيات التي لم تتغيّر

- الموظف لا يستطيع تعديل عقار موظف آخر (403).
- المدير لا يستطيع تعديل/اعتماد عقار فريق آخر (403/404 حسب المسار).
- MANAGER لا يستطيع حذف/Trash (403).
- OWNER يحتفظ بصلاحياته.
- approval المباشر للمشرف المباشر كما هو.
- لا تغيير في assignment أو duplicate detection أو P/A numbering.
- لا تغيير في سجل النظام أو audit التاريخي.

## 6. الاختبارات

### اختبار الرؤية الجديد

```text
property-company-wide-visibility.spec.ts  → 4/4
```

يغطي:

- PENDING مخفي عن الفريق الآخر قبل الاعتماد.
- بعد الاعتماد يظهر للمدير والموظف من فريق آخر.
- التفاصيل والصور متاحة، لكن بدون contact/contactId/reviewNotes/proposedOwner/duplicateCandidateIds.
- الوصول المباشر إلى Contact يعطي 404.
- تعديل/حذف/اعتماد الفريق الآخر ممنوع.
- البحث بالكود والحي، الفلاتر، وpagination عبر الفرق.
- PENDING/REJECTED/TRASHED لا تظهر للفريق الآخر.
- المنشئ والمراجع يحتفظان بوصولهما المشروع.
- موظف من فريق آخر يستطيع ربط العقار المعتمد بطلب عميل للمطابقة.

## 8. حدود وملاحظات

1. الرؤية المشتركة تشمل `AVAILABLE` فقط، تماشيًا مع تبويب «العقارات» الحالي. `SOLD/RENTED/ARCHIVED` تبقي سلوكها السابق ولا تظهر ككتالوج معتمد مشترك.
2. عدّادات التبويبات في الواجهة تعتمد على الصفوف المحمّلة (نافذة الصفحات الحالية) وليست endpoint إجمالي مستقل؛ هذا سلوك موجود مسبقًا. الـAPI pagination والبحث على الخادم دقيقان.
3. المدير يرى العقار المعتمد لفريق آخر كبيانات عامة فقط؛ لا يحصل على جهة الاتصال حتى لو كان مديرًا. هذا مقصود لحماية الخصوصية.
4. سجل النظام لم يتغيّر، ودرج التفاصيل read-only كما هو.
