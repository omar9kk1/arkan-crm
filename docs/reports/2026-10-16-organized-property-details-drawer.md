# تنظيم درج تفاصيل العقار — الموظف والمدير

- **التاريخ:** 2026-10-16
- **الحالة:** التنفيذ والفحوصات البرمجية `Completed`؛ المراجعة البصرية اليدوية `Not Tested`، ينفذها مالك المشروع حسب الطلب.
- **النطاق:** تخطيط المعلومات داخل الدرج، ونقل الحقول المنظمة الموجودة أصلًا في API إلى نموذج العرض.

## التشخيص

راجعت النموذج الفعلي `new-property-model-v2.ts`، استدعاءات الإرسال داخل المعالج، محوّل `property-adapter.ts`، أنواع DTO الأمامية، و`property.dto.ts` و`property-serializer.ts` في الخلفية، ودرجَي الموظف والمدير.

الحقول المنظمة موجودة في استجابات القائمة والتفاصيل: الموقع، المساحة، السعر، التفاوض، مصفوفة `floors`، والعقار المطلوب. لكن محوّل العرض القديم كان يختزل الموقع إلى `region/address`، ويجمع الأدوار في `rooms` باستخدام ` | `، ولا ينقل بيانات البدل والتفاوض أو عدد الأدوار إلى الدرج. كما كان الدرج يعرض `م²` دون قيمة، وسبب تخصيص افتراضي، وملخصًا مولّدًا يكرر البيانات.

## التنفيذ والتخطيط

أُنشئ مكوّن أقسام مشترك لكلا الدرجين، مع نموذج `PropertyDetails` ينسخ حقول API المطلوبة صراحةً. لا يستنتج أدوارًا أو مواقع من الوصف، ولا يجلب جهات اتصال إضافية.

| الترتيب / القسم | الحقول المعروضة ومصدرها |
| --- | --- |
| 1. الرأس الثابت | العنوان `title`، حالة العرض الحالية، المرجع `reference`، زر الإغلاق الحالي |
| 2. صورة العقار | الصورة الحقيقية من `usePropertyImage(id)` عبر المسار المؤمّن؛ لا صورة معمارية بديلة. يظهر إشعار تحميل/تعذر تحميل عند الحاجة |
| 3. الموقع | `governorate`, `district`, `block`, `plotNumber`, `address`؛ العنوان من DTO نفسه فقط، لا العنوان المركب الذي يولده المحوّل القديم |
| 4. السعر والمساحة | `askingPrice` بصيغة عربية ود.ك حتى 3 منازل عشرية؛ `negotiable`: نعم/لا/غير محدد؛ `sizeSqm` فقط عند وجودها |
| 5. الأدوار والمبنى | `floorCount` كما ورد، بما فيه صفر؛ كل `PropertyFloor` في بطاقة مستقلة مرتبة حسب `sortOrder`، باسم `customLabel` أو تسمية `type`، ونص `details` كاملًا |
| 6. الوصف العام | `description` النصي الحقيقي كاملًا، دون إعادة الملخص المولّد للمعالج |
| 7. العقار المطلوب | يظهر فقط لـ`EXCHANGE`: المحافظة والمنطقة والقطعة والقسيمة والمساحة، ثم `floorRequirements` و`notes`، و`budgetMin` و`budgetMax` كل منهما مستقل |
| 8. المسؤولية والتواصل | `responsibleName`؛ ونوع المالك/الوسيط واسمه وهاتفه من `contact` الخاص الذي أعاده الخادم فعلًا |
| 9. المراجعة | `reviewStatus` و`reviewNotes` من DTO الخاص فقط، وزر الموظف الحالي «تعديل وإعادة إرسال» بشروطه السابقة |

- تشمل أنواع الأدوار: الأرضي والأدوار المرقمة والسرداب ونصف الدور وربع الدور والسطح والميزانين والأدوار المخصصة.
- تستخدم الملاحظات `white-space: pre-wrap` والتفافًا آمنًا؛ لا اقتطاع أو حد طول بصري أو دمج بين سجلات الأدوار.
- القيم الفارغة لا تنشئ بطاقات. تُحذف الأقسام الخالية؛ حالة التفاوض غير المعروفة قيمة عرض صريحة «غير محدد».
- لا يظهر «غير مخصص لك» أو قسم تخصيص وهمي.
- عرض الدرج 560px على سطح المكتب، وعرض الشاشة ناقص 16px على الهاتف. الرأس خارج منطقة التمرير، باستخدام بنية `PropertyOverlay` الأصلية.
- الإغلاق وEscape وحصر التركيز وإعادته بقيت ضمن dialog الأصلي. أُضيفت خاصية `headerDetails` اختيارية؛ النوافذ التي لا تمررها، ومنها المعالج، تحتفظ ببنية عنوانها السابقة.
- سجل المتابعات الحالي محفوظ عندما توجد بيانات له. لا يولّد التطبيق بيانات متابعة جديدة.

## الوصف المولّد وعدم اختراع البيانات

`buildDescription` الحالي يكتب JSON يعيد بيانات المعالج، ويضيف ملخصًا نصيًا للبدل. يتعرف `generalPropertyDescription` على هذا الغلاف فقط **لمنع عرضه مكررًا أو خامًا**؛ لا يستخرج منه أي حقول أو أسماء أو أرقام أو أدوار. الحقول المنظمة مصدرها DTO حصريًا. الوصف النصي العادي يبقى كاملًا، ولا يُحذف محتواه بالتخمين أو المطابقة التقريبية.

## الخصوصية

- للموظف الذي يرى عقار موظف آخر: بيانات عامة واسم المسؤول فقط؛ `contact/reviewStatus/reviewNotes` الخاصة غير موجودة في DTO العام.
- يُنقل فقط `contact.type/name/phone` إذا أعاد الخادم جهة اتصال؛ لا استنتاج من `owner` القديم، ولا بحث بالهاتف، ولا استدعاء سجل جهات التواصل.
- `contact.notes` ومعرّفات الاتصال ومسارات التخزين ونص واتساب الخام غير موجودة في نموذج التفاصيل الجديد.
- عندما يكون `contact: null` داخل DTO خاص، تبقى جهة الاتصال مخفية؛ يمكن عرض ملاحظات المراجعة التي صرّح بها الخادم بشكل مستقل.
- لم تتغير قواعد تفويض الخلفية أو واجهات الموافقة والرفض وطلب التعديل. أزرار المدير الموجودة في قائمة المراجعة بقيت في مكانها ومساراتها الحالية؛ لم تكن داخل درج المدير أصلًا.

## فجوات الربط الموجودة مسبقًا — موثقة دون تغيير الإرسال

1. **إضافات المبنى دون ملاحظات:** `mapFloors.appendFlag` لا يقرأ `hasBasement/hasHalfFloor/hasQuarterFloor`؛ إذا فُعّل الخيار وكانت ملاحظاته فارغة ولم يوجد سجل بنفس النوع، لا يُرسل `PropertyFloor`. والعكس: نص محفوظ لإضافة أُلغي اختيارها قد يُرسل رغم إلغاء الاختيار. يعرض الدرج ما حُفظ في API فعلًا، ولا يعيد بناء الخيارات من JSON.
2. **دمج النوع المتكرر:** إذا كان هناك دور من نوع BASEMENT/HALF/QUARTER ومعه ملاحظات الإضافة العامة، يدمجها المحوّل داخل `details` لنفس السجل باستخدام ` | `. لا توجد في DTO هوية مستقلة للنص المدموج لفصله بأمان. لا يقسمه الدرج تخمينيًا.
3. **الإضافات داخل الدور القديم:** حقول `floor.hasBasement/...` القديمة تُدمج في `details` للدور نفسه أثناء الإرسال؛ ليست سجلات مستقلة في API.
4. **عدد الأدوار:** عند عدم وجود أي سجل دور لا يرسل `sharedPayload.floorCount`، حتى لو كانت قيمة النموذج صفرًا. أما عند وجود إضافات فقط فقد يُرسل صفرًا. يعرض الدرج العدد فقط إذا أعاده API، ولا يحسب قيمة بديلة قد تخلط الأدوار الأساسية بالإضافات.
5. **مساحتا landArea/unitArea القديمتان:** API يحتوي `sizeSqm` واحدًا؛ القيمة الموحدة وحدها تُرسل كحقل منظم، والقيم القديمة الأخرى قد تبقى في غلاف الوصف. لا تُعرض كمساحات مستقلة مُخترعة.
6. **الوصف العام والعنوان والعنوان النصي للعقار:** DTO يدعمها، لكن المعالج الحالي لا يحتوي حقول إدخال مستقلة لها؛ `sharedPayload` يكتب وصفًا مولّدًا ولا يرسل `address/title` يدويين. يعرض الدرج النص الحقيقي إذا جاء من API، ويخفي غلاف المعالج المكرر. نص الواتساب الخام لا يُستخدم كبديل للوصف العام.
7. **دقة الإدخال المالية:** `toDecimalString` الحالي يقبل منزلتين عشريتين فقط للحقول التي يستخدمها. العرض يدعم حتى 3 منازل للدينار عند ورودها؛ لم يُغيّر قبول الإدخال أو مخطط الأسعار.
8. **التخصيص والمتابعات:** DTO الحالي لا يحمل سبب تخصيص أو تاريخ متابعات؛ لا تُعرض أسباب افتراضية أو بيانات وهمية.
9. **نموذج المدير السابق:** كان يفقد الهاتف والمراجعة والتفاوض والبدل والأدوار المنظمة. صُحح فقد العرض عبر `details` المشترك، دون تعديل DTO أو API.

هذه الفجوات في الإرسال تحتاج مهمة مستقلة وموافقة؛ لم يُعدّل المعالج أو قاعدة البيانات لمعالجتها ضمن هذه المهمة.

## التحقق

شُغّل فحص مركز باستخدام الأدوات الموجودة Node/TypeScript/React server rendering، مع محاكاة hook الصورة فقط ودون طلبات API أو كتابة قاعدة بيانات:

- DTO عام دون اتصال أو مراجعة خاصة.
- DTO خاص لوسيط مع اسم وهاتف ومراجعة؛ عدم نقل أو عرض ملاحظات جهة الاتصال السرية.
- DTO خاص ذو `contact: null` مع مراجعة مسموح بها.
- سبعة أنواع أدوار مستقلة وترتيبها، وظهور كل نص مرة واحدة مع أسطره ونصوصه الطويلة.
- عدم عرض مساحة فارغة أو تخصيص افتراضي، والحفاظ على عدد أدوار صفر.
- بدل بميزانية قصوى فقط، ودنيا فقط بما فيها صفر، وإخفاء الطلب في البيع.
- إخفاء غلاف JSON ونصه الخام، وعدم اختراع أدوار منه، وإبقاء الوصف العام الحقيقي.
- تطابق `details` بين محوّلي الموظف والمدير.

**النتيجة: نجحت جميع التأكيدات.** فحص النوع الأول أظهر مشكلات narrowing/null في الملف الجديد؛ صُححت ثم نجحت الفحوصات التالية.

## حدود التحقق والتوقف

لم أُثبّت أدوات أتمتة متصفح، ولم أدّعِ إجراء مراجعة بصرية جديدة. اختبار المتصفح اليدوي، وتجربة الهاتف الفعلي والتمرير والتركيز، واختبار تدفق الموافقة/الرفض الفعلي متروكة لمالك المشروع حسب التعليمات. البيانات القديمة التي لا تمر عبر محوّل API ولا تحمل `details` لا يُعاد اختراع تفاصيلها من وصف مركب.
