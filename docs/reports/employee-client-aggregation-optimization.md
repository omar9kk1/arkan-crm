**النطاق:** تجميع `client_counts` في صفحة الدليل وملخصه فقط.  
**الحالة:** مكتمل — **NO-GO: لا تغيير إنتاجي** (لا توجد صيغة أسرع بشكل متسق في كل من الخدمة والتزامن).

**الخلاصة:** الصيغة الحالية `UNION` + `COUNT(*)` هي الأفضل أو مساوية لكل البدائل في قياسات متناوبة. `UNION ALL + COUNT(DISTINCT)` و`DISTINCT` pairs لم تتفوق باستمرار، و`JOIN` المباشر مع `OR` أبطأ 1.6–2×. صيغة ملخص `COUNT(DISTINCT (profile, client))` أبطأ 2–3×. لم يُغيَّر الكود.

## 2. الصيغة الحالية والخطة

```sql
client_pairs AS (
  SELECT c."createdById" AS profile_id, c.id FROM "Client" c WHERE c."createdById" IS NOT NULL
  UNION
  SELECT c."responsibleEmployeeId", c.id FROM "Client" c WHERE c."responsibleEmployeeId" IS NOT NULL
),
client_counts AS (
  SELECT s.profile_id, COUNT(*)::int AS metric
  FROM client_pairs cp JOIN scoped s ON s.profile_id = cp.profile_id
  GROUP BY s.profile_id
)
```

`EXPLAIN (ANALYZE, BUFFERS)` على Stage C (OWNER، 4,501 مجموعة، 13,535 زوجًا مميزًا):

| الخطوة | الزمن | Buffers |
|---|---:|---:|
| Seq Scan ×2 على `Client` (13,535 صفًا لكل عمود) | 2.9 + 2.4 ms | 265 + 265 |
| Append (27,070 صفًا) | 7.5 ms | 530 |
| HashAggregate على `(createdById, id)` → 13,535 زوجًا | 18.0 ms | 1,809 kB |
| Hash Join مع 5,000 `EmployeeProfile` ثم `User` | 28.7 ms | 786 |
| HashAggregate لكل موظف (4,501) | 32.8 ms | 721 kB |
| **الإجمالي** | **35.3 ms** | hit فقط |

- توجد فهارس على `Client.createdById` و`Client.responsibleEmployeeId`، لكن المخطط يختار Seq Scan لأن مسح 13.5k صفًا أرخص من index scan كامل للجدول في هذا الحجم.
- التكلفة جوهرية: قراءة الجدول مرتين (عمودان) + إزالة التكرار + ربط 5,000 ملف + تجميع. لا توجد إعادة كتابة بسيطة تُلغي هذا العمل دون تغيير المخطط.

## 3. البدائل المقاسة

### أ) تجميع الصفحة (نفس `scoped`)

| الصيغة | OWNER median | MANAGER median |
|---|---:|---:|
| **A: UNION + COUNT(*)** (الحالية) | **29.1 / 37.7 / 31.9 ms** | 25.9 / 26.5 / 34.5 ms |
| B: UNION ALL + COUNT(DISTINCT id) | 33.0 / 35.7 / 44.6 ms | 25.1 / 26.1 / 26.7 ms |
| C: UNION ALL + SELECT DISTINCT ثم COUNT(*) | 32.9 / 34.3 / 41.2 ms | 23.1 / 23.8 / 26.7 ms |
| D: JOIN مباشر مع OR + COUNT(DISTINCT) | **61.2 ms** | **34.6 ms** |

(ثلاث جولات متناوبة؛ القيم متقلبة ±15% بسبب الحمل الخلفي.)

- B وC داخل نطاق تباين A في بعض الجولات، لكن **لا يتفوقان باستمرار** على A في النطاقين.
- D أبطأ بوضوح (1.6–2×) لأن شرط `OR` يمنع ربطًا فعّالًا.
- جميع الصيغ أعادت **نفس النتائج حرفيًا** (`sameAB/sameAC/sameAD = true`): OWNER 4,501 مجموعة / 13,535 عميلًا، MANAGER 2,476 / 7,460.

### ب) تجميع الملخص

| الصيغة | OWNER | MANAGER |
|---|---:|---:|
| الحالية (GROUP BY ثم SUM) | **48.8 ms** (تنفيذ 49.0) | **41.7 ms** (45.3) |
| `COUNT(DISTINCT (profile_id, client_id))` | **136.6 ms** (173.4) | **83.5 ms** (87.7) |

الصيغة البديلة أبطأ 2–3× (composite DISTINCT يفرض فرز/تجميعًا أكبر)، مع تطابق القيم (`total/active/clients_total/late_total` متطابقة).
