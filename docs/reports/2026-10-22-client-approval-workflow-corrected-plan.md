# خطة سير عمل موافقات إنشاء وتعديل العملاء — القيود المصحّحة

- **المشروع:** ARKAN CRM
- **التاريخ:** 2026-10-22
- **الحالة:** مقترح معماري معدّل — **بانتظار موافقة المالك النهائية قبل أي تنفيذ أو ترحيل** (لم يُنفَّذ شيء؛ لم تُطبَّق ترحيلات؛ لم تُلمس قواعد البيانات).

---

## السياق

خضع مقترح بنية «مراجعات الموظفين لإنشاء/تعديل العملاء» (يستعيد نمط إقرارات العقارات: `PropertyApprovalRequest` / `PropertyRevision`) لمراجعة المالك، وصُحّح البندان التاليان قبل التنفيذ:

1. **حذف** القيد الجزئي المقترح سابقًا على `requestedById` لمراجعات الإنشاء المعلّقة — يجب أن يستطيع الموظف الواحد إرسال **عدة عملاء جدد مختلفين باتفاق** لمراجعة المدير. الإبداع يُعمل عبر معرّف مراجعة فريد + آلية idempotency، لا عبر قيد «طلب معلّق واحد لكل موظف».
2. **تعديلات العملاء:** مراجعة **نشطة واحدة** فقط لكل `Client.id` بحالات PENDING **و** CHANGES_REQUESTED معًا. إعادة الإرسال تستمر على **نفس** صف المراجعة (لا طلبات متعارضة)، وعند الموافقة يُتحقّق من خط الأساس الموثوق ويعاد 409 آمن عند أي تعارض.

### المتطلبات المُبقاة كما كانت

- إنشاءات الموظفين المعلّقة **لا تظهر** في قوائم العملاء الموثوقة/البحث/الإحصائيات إطلاقًا.
- بيانات العميل الموثوقة **لا تتغير** ما دام التعديل معلّقًا.
- المدير والموظف يتشاركان واجهة Astra نفسها والساحر رباعي الخطوات نفسه (بلا تكرار مكوّنات).
- لا تعرّض لبيانات عملاء موظف آخر؛ 404 صامت للمرفوض.
- الموافقة تطبّق تعديلات العميل واستفسارات العقارات **ذرّيًا**.
- الإشعارات مُزوَّرة وفيها تفاصيل آمنة فقط.
- العملاء الحاليون وعلاقاتهم (متابعات/جهات/استفسارات) سليمة حتى موافقة صحيحة.

## 1) قيود المخطط (بعد التصحيح)

ترحيل واحد إضافي بالكامل — جداول جديدة + عمود إخباري، بلا أي تعديل على أعمدة موجودة:

### جدول `ClientReviewRequest`

| العمود | النوع / الوصف |
|---|---|
| `id` | `UUID @id @default(uuid())` — معرّف المراجعة الفريد نفسه هو المرجع للـ idempotency والروابط العميقة |
| `kind` | `('CREATION' \| 'EDIT')` |
| `clientId` | `UUID?` — **null** للإنشاء، معرّف العميل للتعديل؛ FK Restrict |
| `payload` | `Json` — البيانات **المقترحة كاملة**: الاسم/الهاتف/الملاحظات/`requestData`/الاستفسارات المختارة مع سبب وملاحظات لكل استفسار |
| `base` | `Json?` (للتعديل فقط) — لقطة الحالة الموثوقة عند الإرسال **+ `Client.updatedAt` وبصمة الاستفسارات المرتبطة** لكشف التعارض |
| `idempotencyKey` | `UUID?` — يولّده الساحر ويبقى ثابتًا ما بقي الساحر مفتوحًا على نفس الجلسة |
| `status` | `ApprovalStatus` (نفس enum العقارات: PENDING / APPROVED / REJECTED / CHANGES_REQUESTED) |
| `requestedById` | `UUID` FK |
| `reviewedById` | `UUID?` FK |
| `reviewNotes` | `String?` |
| `createdAt` / `reviewedAt` | `DateTime @default(now())` / `DateTime?` |

فهارس: `(status, createdAt)` و `(requestedById)`.

فهرس فريد جزئي للـ idempotency:

```
UNIQUE (idempotencyKey) WHERE idempotencyKey IS NOT NULL
```

### الفهرس الجزئي النظامي — مراجعة نشطة واحدة لكل عميل (كما صحّح المالك)

SQL خام داخل الترحيل، بأسلوب فهرس `PropertyRevision_one_pending_per_property` القائم (لا يُذكر في schema.prisma):

```
client_review_active_edit_per_client:
UNIQUE (clientId)
WHERE kind = 'EDIT' AND clientId IS NOT NULL
  AND status IN ('PENDING', 'CHANGES_REQUESTED')
```

- يمنع على **مستوى قاعدة البيانات** أكثر من مراجعة نشطة واحدة لكل `Client.id` — سواء أكانت PENDING أم CHANGES_REQUESTED.
- قرار APPROVED أو REJECTED تاريخي **لا يمنع** فتح مراجعة تعديل جديدة.
- **لا قيد على requestedById نهائيًا** — الموظف يرسل عدة عملاء جدد متزامنين كما يريد.

### عمود إخباري وحيد على جداول موجودة

- `Notification.reviewId UUID?` — للربط العميق لمراجعات العملاء. لا تعديل آخر على أي جدول موجود.

## 2) Idempotency للإنشاء (بديل القيد المحذوف)

- `POST /client-reviews` يقبل `idempotencyKey` اختياريًا:
  - إن وُجد صف بنفس المفتاح → يُعاد **نفس** المراجعة (استجابة 200 لا إنشاء جديد). إعادة النقر أو انقطاع الشبكة لا يولّدان صفوفًا مزدوجة.
  - من دون مفتاح: كل إرسال مراجعة جديدة سليمة (عمدًا — عملاء مختلفون متزامون).
- ملاحظة: منع التكرار اللحظي داخل نفس الضغطة (نقر مزدوج) يبقى عبر تعطيل زر الإرسال في الواجهة + فحص خفيف لنفس (الموظف، CREATION، بصمة payload) خلال المهلة نفسها — اختياري ولا يقيّد أي حالة مشروعة.

---

## 3) دورة الحياة وانتقالات الحالة

- **الإنشاء:**
  - PENDING → APPROVED (يولّد صف `Client` + استفساراته داخل نفس المعاملة) | REJECTED | CHANGES_REQUESTED.
  - إعادة الإرسال من CHANGES_REQUESTED → PENDING **على نفس الصف بنفس المعرّف** (لا قيد يخص الإنشاء فلا تعارض).
- **التعديل:**
  - الفهرس الجزئي يعني أن إعادة الإرسال **يجب** أن تستمر على صف المراجعة القائم: `PATCH /client-reviews/:id` يُقبل فقط من صاحب المراجعة وحالة PENDING/CHANGES_REQUESTED، يعيد حساب `payload`، **يُحدّث `base` إلى لقطة الحالة الموثوقة الحالية** (إعادة تقديس)، ثم يرفع الحالة إلى PENDING. السجل لا يتضاعف أبدًا — والفهرس يضمن ذلك بنيةً تحتية.
- **الحماية من القرارات المتكررة (claim قبل القرار):**
  - أول عملية في معاملة القرار: تحديث شرطي
    `UPDATE ... SET reviewedById, status = '$NEXT' WHERE id = :id AND status = 'PENDING'`
    — صفر صفوف متأثرة → 409 «قرار سُجّل سابقًا» (موافقة/رفض مزدوج أو سباق مديرين آمن).

---

## 4) معاملة الموافقة — ذرّية وبلا تعارض

### الموافقة على تعديل (داخل `prisma.$transaction` بعزل Serializable على Postgres)

1. **Claim:** تحديث شرطي لصف المراجعة (القسم 3) — الخاسر يُرفض بـ 409 فورًا.
2. **التحقّق من خط الأساس:** قراءة صف العميل الفعلي داخل نفس المعاملة، ومقارنة `updatedAt` وبصمة (الاسم/الهاتف/الملاحظات/`requestData`/الاستفسارات) مع `base` المخزّن.
3. **عدم تطابق → فشل المعاملة كاملًا** و409 برسالة آمنة «تغيّرت بيانات العميل أثناء المراجعة؛ أُعد الإرسال» — المراجعة **تبقى نشطة** (PENDING/CHANGES_REQUESTED) ولم يُمس أي شيء، والمدير يرى تنبيه التعارض في واجهة المراجعة.
4. **تطابق → تطبيق كل شيء في نفس المعاملة:** أعمدة العميل + `requestData` + الاستفسارات (upsert/deleteMany بنفس منطق المسارات الحالية) + سجل تدقيق `CLIENT_REVIEW_APPLY` + إشعار القرار للموظف. أي فشل يرتجع حتى تغيير حالة المراجعة.

### الموافقة على إنشاء

النمط نفسه: إنشاء صف `Client` + استفساراته + تدقيق + إشعار داخل معاملة واحدة، مع claim الشرطي نفسه؛ فشل الإنشاء يُعيد المراجعة إلى PENDING (لم يُسجّل قرار).

---

## 5) الإشعارات (مُزوَّرة المفاتيح)

- **إرسال/إعادة إرسال** → المدراء النشطون، بمفتاح حدث يتضمّن طوابع زمنية للإرسال: كل إرسال حقيقي يولّد إشعارًا واحدًا.
- **القرارات** (موافقة/رفض/طلب تغيير) → للموظف الطالب، بمفتاح ثابت:
  `client-review:decided:<reviewId>:<decision>` — قرارات متكررة أو سباقات لا تولّد نسخًا مزدوجة.
- **الخصوصية:** المحتوى حقائق آمنة فقط (أسماء حقول وتغييرات غير حسّاسة مثل «الميزانية: من X إلى Y») — بلا هواتف ولا ملاحظات ولا نصوص رسائل، وفق قواعد الخصوصية القائمة. نفس بنية الإشعارات ودعم Web Push والروابط العميقة الحالية.

## 6) نقاط النهاية والصلاحيات (ملخّص)

| المسار | الدور | السلوك |
|---|---|---|
| `POST /client-reviews` | موظف | إرسال إنشاء/تعديل للمراجعة؛ المدير يتجاوز المراجعة (حفظه المباشر عبر المسارات الحالية) |
| `GET /client-reviews` | مدير: الكل / موظف: مراجعاته فقط (`requestedById`) | تبويب «تحت المراجعة» |
| `GET /client-reviews/:id` | صاحب المراجعة أو مدير | المقترح + **الفرق المضبوط** مقابل النسخة الموثوقة (بخصوصية) |
| `PATCH /client-reviews/:id` | صاحب المراجعة، PENDING/CHANGES_REQUESTED فقط | إعادة إرسال على نفس الصف + إعادة تقديس `base` |
| `POST …/approve \| reject \| request-changes` | مدير فقط | claim شرطي + معاملة ذرّية + 409 عند التعارض/التكرار |

---

## 7) واجهة المستخدم (بعد الموافقة)

- تبويب مشترك «تحت المراجعة» في صفحتي المدير والموظف (مكوّن واحد مشترك: بطاقات المراجعة + عرض الفرق + أزرار المدير)، وساحر الإرسال يظل الساحر رباعي الخطوات نفسه بلا تكرار.

## 8) التراجع

إسقاط جدول `ClientReviewRequest` وفهرسه الجزئي وعمود `Notification.reviewId` فقط — جدول العملاء وعلاقاته لا يُمسان في هذا الترحيل إطلاقًا.

---

## 9) اختبارات مركّزة — `client-review-workflow.spec.ts`

1. إنشاء تحت مراجعة: غائب عن القوائم/ الإحصائيات/ البحث؛ يظهر لصاحبه في «تحت المراجعة»؛ 404 لموظف آخر.
2. المدير يرى كل المراجعات المعلّقة من كل الموظفين.
3. موافقة إنشاء → العمليّة تحدث ذرّيًا (Client + استفسارات)؛ موافقة مزدوجة → 409.
4. **عدة إنشاءات متزامنة من نفس الموظف** تنجح كلها (غياب قيد requestedById)؛ إعادة إرسال بنفس `idempotencyKey` تعيد صف المراجعة نفسه (لا صف إضافي).
5. تعديل تحت مراجعة: الصف الموثوق لا يتغير أبدًا؛ المدير يرى الفرق الدقيق (`requestData` والاستفسارات الإضافة/الإزالة).
6. موافقة تعديل → تطبيق ذرّي؛ تطبيق الاستفسارات؛ المتابعات/التدقيق سليمة.
7. **تعارض:** العميل تغيّر بعد الإرسال → موافقة → 409 آمن، المراجعة تبقى نشطة، لا شيء تُطُبّق جزئيًا.
8. مراجعتا تعديل لنفس العميل → الثانية محجوبة بالفهرس الجزئي؛ إعادة الإرسال تستمر على نفس الصف.
9. الإشعارات: مفاتيح القرار مُزوَّرة، وكل إرسال إشعار واحد، وبلا تفاصيل خاصة في المعاينات.
