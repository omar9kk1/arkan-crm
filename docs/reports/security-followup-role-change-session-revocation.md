## 2. الأدلة

**الاختبارات المعزولة:** `apps/backend/test/role-change-session-revocation.spec.ts`  
**النتيجة:** **7/7 ناجحة** + **6 حزم / 65 اختبارًا** ذات صلة (auth, cookie mode, refresh DB, employees, push) ناجحة.  
`typecheck` و`eslint` للملف: 0 أخطاء.

الأدلة من الكود:

- `auth.service.ts` (refresh): يقرأ الدور الحالي من DB عبر `current.user` ويُصدر التوكن به (`issueTokens`). لا يقارن دور التوكن القديم ولا يُبطل العائلة عند تغيّر الدور.
- `jwt-auth.guard.ts`: يرفض فقط إذا `session.user.role !== payload.role`. هذا **بوابة اختلاف** وليس إبطالًا.
- `employees.service.ts` (setActivation): عند التعطيل ينفّذ `refreshToken.updateMany({ revokedAt })`، والتعليق يصرّح: «Deactivating revokes every existing session, so a disable → enable cycle can never resurrect tokens issued before the deactivation».
- `docs/reports/security-phase2-auth-session-plan.md` (السطور 49–50): تعطيل الحساب يلغي كل RefreshTokens، والـGuard يتحقق من `isActive` وتطابق الدور، أي «إبطال الرموز الحالية عند الطلب التالي» — وليس إبطالًا دائمًا عند تغيير الدور.

`setActivation` يستهدف `role: EMPLOYEE` فقط؛ لذلك Manager لا يمكن تعطيله عبر الـAPI.

## 3. هل هو Bug أم سياسة مقصودة؟

### تعطيل الحساب — **مقصود وسليم**
- الإبطال الدائم منفّذ بوضوح في `setActivation`، ومغطى باختبارات.
- إعادة التفعيل لا تحيي الجلسات القديمة.
- **ليس Bug.**

### تغيير الدور — **فجوة تصميم / سياسة غير محسومة**
- لا يوجد إبطال جلسات عند تغيير الدور (بخلاف التعطيل).
- الـGuard يمنع الوصول مؤقتًا فقط عند اختلاف الدور.
- الـrefresh يُصدر الدور الجديد فورًا دون إعادة تحقق.
- إعادة الدور إلى القيمة الأصلية تُحيي Access قديمًا لم يُدوّر.

**التصنيف الأدق:** ليس Bug واضحًا في التنفيذ مقابل تعليق صريح، بل **سياسة ناقصة/غير متسقة**:
- إذا كانت السياسة المقصودة «تغيير الدور يطبّق فورًا على الجلسات الحية» → السلوك الحالي متسق، لكنه يسمح بترقية الصلاحية دون إعادة مصادقة.
- إذا كانت السياسة المقصودة «تغيير الدور يبطل الجلسات نهائيًا» → السلوك الحالي **Bug**، لأن إعادة الدور تحيي التوكنات، ولأن refresh قديم يمنح Manager بعد الترقية.

**التوصية:** اعتماد سياسة صريحة: **أي تغيير دور أو تعطيل أو تغيير كلمة مرور يجب أن يبطل كل الجلسات ويجبر إعادة الدخول**، مع استثناء موثق إن أُريد خلاف ذلك.

## 4. الأثر الأمني

**Medium** — لا يوجد استغلال عن بُعد مباشر، لكنه يمس احتواء الحوادث:

1. **ترقية Employee → Manager:** أي RefreshToken صادر قبل الترقية (جهاز قديم، نسخة احتياطية، token مسروق) يحصل على وصول Manager كامل دون كلمة مرور.
2. **خفض Manager → Employee:** لا يُنهي الجلسة؛ المستخدم يبقى موثقًا بدور Employee. إذا كان الخفض إجراء احتواء، فهو لا يطرد المهاجم.
3. **Manager → Employee → Manager:** Access قديم لم يُدوّر يعود صالحًا بعد إعادة الدور. إذا كان الخفض مؤقتًا، فالتوكن الملتقط قبل الخفض قد يعود بصلاحية Manager.
4. **تعطيل Manager:** لا مسار API؛ التعطيل المباشر في DB لا يبطل الجلسات، فإعادة التفعيل تُحييها.
5. **تعطيل مباشر في DB لأي حساب:** نفس خطر الإحياء؛ يجب استخدام الـAPI أو إبطال التوكنات يدويًا.
6. **المتصفحات الأخرى:** تتأثر جميعها بشكل موحد بتغيير الدور (تُحجب) لكنها تبقى قادرة على refresh إلى الدور الجديد؛ التعطيل عبر API يبطلها كلها.

**ما لا يتأثر:** تعطيل الموظف عبر الـAPI، تسجيل الخروج، تدوير refresh، منع إعادة الاستخدام، وWeb Push (الاشتراك المرتبط بـlineage مُبطلة يتوقف).

## 5. الإصلاح الآمن المقترح (يحتاج اعتمادًا — لم يُنفّذ)

### الخيار الموصى به: `authVersion` مركزي
- إضافة عمود `authVersion` (عدد صحيح) إلى `User` (Prisma schema + migration — يحتاج اعتمادًا).
- تضمينه في JWT claim وفي صف `RefreshToken`.
- زيادته ذريًا عند: تغيير الدور، التعطيل، تغيير كلمة المرور، وأي إجراء احتواء.
- `JwtAuthGuard` يرفض إذا اختلف `authVersion`؛ `refresh` يرفض ويُبطل العائلة إذا اختلف.
- ميزة: يغطي كل أنواع تغيير الحساب، وليس الدور فقط.

### بديل بلا Schema (سلوك مصادقة — يحتاج اعتمادًا)
- عند تغيير الدور عبر مسار إداري مركزي: تحديث الدور + `refreshToken.updateMany({ userId, revokedAt: null }, { revokedAt: now })` في نفس المعاملة.
- ثم كل Access قديم يفشل (session revoked) وكل Refresh يفشل → login جديد.
- العيب: يحتاج مسارًا إداريًا موحدًا؛ أي SQL مباشر يتجاوزه.

### بديل مرتبط بالدور فقط (Schema)
- إضافة `roleAtIssue` إلى `RefreshToken`؛ عند الـrefresh إذا اختلف عن دور DB → إبطال العائلة و401.
- يغطي الترقية/الخفض لكن ليس تعطيل/كلمة مرور.

### تحسينات تشغيلية فورية دون تغيير سلوك
- منع تعطيل/تغيير دور أي حساب عبر SQL مباشر؛ استخدام الـAPI أو سكربت إداري يبطل `RefreshToken` صراحةً.
- إضافة مسار إداري لتعطيل Manager (حاليًا 404) يبطل جلساته.
- توثيق أن تغيير الدور عبر SQL **لا** يبطل الجلسات.

**لا يُنصح** بالاعتماد على `iat` مقابل `User.updatedAt` لأن أي تعديل اسم/تفضيلات سيُطرد كل الجلسات، وهو حساس للساعة.

## 6. اختبارات الانحدار المطلوبة بعد اعتماد الإصلاح

1. **تعطيل عبر API:** كل الجلسات (أكثر من متصفح) → access/refresh 401، وإعادة التفعيل لا تحييها، وlogin جديد يعمل. *(موجود حاليًا ويجب أن يبقى.)*
2. **تعطيل مباشر في DB:** يجب أن يُبطل عبر trigger/سكربت، أو يُوثّق كمسار غير مدعوم.
3. **Manager → Employee:** access قديم 401، وrefresh قديم 401 (أو دور Employee حسب السياسة)، ولا وصول Manager.
4. **Employee → Manager:** access قديم 401، و**refresh قديم 401/يتطلب login**، ولا وصول Manager بدون مصادقة جديدة.
5. **Manager → Employee → Manager:** Access/Refresh الصادران قبل التغيير يبقيان غير صالحين؛ لا إحياء.
6. **جلسات متعددة:** كل الجلسات تُبطل عند تغيير الدور؛ لا جلسة تبقى قادرة على refresh.
7. **Cookie + Legacy/Dual:** نفس النتيجة في كل أوضاع المصادقة.
8. **Web Push:** اشتراك lineage المُبطلة يتوقف عن الاستقبال.
9. **عدم كسر:** تدوير refresh، سباق refresh/logout، تسجيل الخروج، والجلسات العادية.
10. **تحديث الاختبارات الحالية:** `security-task7-penetration.spec.ts` يؤكد حاليًا عودة الجلسة بعد إعادة الدور (characterization)؛ يجب عكسه بعد اعتماد الإبطال الدائم.
