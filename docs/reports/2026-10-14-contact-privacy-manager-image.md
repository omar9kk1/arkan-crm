## 1. المشاكل المكتشفة

### مشكلة 1 — سجلات COMPANY ظاهرة لكل الموظفين
كانت دالة `canViewContact` في `apps/frontend/lib/contact-registry.ts` تعتبر سجلات النطاق `COMPANY` (بيانات البذرة/المرجع) مرئية تلقائيًا لكل الموظفين:

```ts
if (contact.scope === 'COMPANY') return true;   // ❌ يمنح الموظفين وصولًا غير مصرّح
```

النتيجة: أي موظف يستطيع تصفّح أسماء وأرقام مالكي/وسطاء الشركة، واستخدامهم، ومطابقة أرقامهم، دون أن يكون مسؤولًا عن السجل. هذا يخالف قاعدة العمل (البيانات الخاصة تُرى فقط من المدير ومن الموظف الذي سجّلها).

### مشكلة 2 — العقارات القديمة بلا `ownerUserId` تكشف بيانات الاتصال
كانت دالة `canViewPropertyContact` في `apps/frontend/lib/property-privacy.ts` تعتبر غياب `ownerUserId` إذنًا ضمنيًا:

```ts
if (!property.ownerUserId) return true;         // ❌ يفتح بيانات المالك/الهاتف لأي موظف
```

النتيجة: كل عقارات العينة القديمة (بلا هوية مالك مسجّلة) كانت تعرض اسم المالك ورقمه لكل موظف. غياب الهوية يعني أن الموظف المسؤول غير معروف، فلا يصح اعتباره إذنًا.

### مشكلة 3 — تسريب الهاتف داخل وصف عقار المدير
كان `apps/frontend/features/manager-properties/components/add-property-modal.tsx` يحقن رقم هاتف المالك داخل نص الوصف الحرّ:

```ts
`هاتف المالك: ${property.phone}`,              // ❌ بيانات اتصال داخل نص غير خاضع للتنقيح
```

الوصف الحرّ لا يخضع لدالة تنقيح البيانات الحساسة (التنقيح يعمل فقط على الوصف المُهيكل بصيغة JSON)، فيبقى الرقم مكشوفًا إن ظهر هذا الوصف لأي موظف غير مخوّل.

### ملاحظة مرتبطة
`apps/frontend/lib/contact-registry.ts` ما زال يُصدّر `companyContactsFor(type)` التي تُعيد سجلات COMPANY دون أي فحص للمستخدم. الدالة **غير مستخدمة حاليًا**، لكنها «قنبلة موقوتة» محتملة (footgun).

## 2. الإصلاحات المُنفّذة (أصغر تغييرات آمنة)

### 2.1 المنع الافتراضي للسجلات (`contact-registry.ts`)
أصبح الوصول للموظف يتطلب ملكية صريحة بهوية ثابتة:

```ts
export function canViewContact(user, contact): boolean {
  if (!user) return false;
  if (user.role === Role.MANAGER) return true;
  // Default deny: explicit, stable ownership is required for employees.
  return !!contact.ownerUserId && contact.ownerUserId === user.id;
}
```

- لا يُعتبر `scope === 'COMPANY'` إذنًا بعد الآن.
- أي سجل بلا `ownerUserId` (أو بنطاق COMPANY) يُرفض افتراضيًا للموظفين.
- المدير يظل يرى كل السجلات.
- الموظف يرى فقط السجلات التي تحمل `AuthUser.id` الخاص به.

### 2.2 المنع الافتراضي لبيانات العقار (`property-privacy.ts`)
```ts
export function canViewPropertyContact(user, property): boolean {
  if (!user) return false;
  if (user.role === Role.MANAGER) return true;
  // Employees need an explicit, stable identity match; unknown ownership denies.
  return !!property.ownerUserId && property.ownerUserId === user.id;
}
```

- أُزيل فرع `if (!property.ownerUserId) return true`.
- العقارات القديمة بلا هوية مالك → بيانات الاتصال مخفية عن الموظفين، ويُعرض بدلًا منها «الموظف المسؤول».
- الموظف الذي سجّل العقار (تطابق `ownerUserId`) يظل يرى بيانات الاتصال.

### 2.3 إزالة تسريب الهاتف من وصف المدير (`manager-properties/add-property-modal.tsx`)
أُزيل السطر الذي يُضمّن `هاتف المالك` داخل الوصف الحرّ. رقم الهاتف يبقى حقلًا مستقلًا (`Property.phone`) يُعرض فقط ضمن مسار مخوّل، ولا يُدمج في نص قد يظهر لغير المخوّل.

### 2.4 تصحيح نص توضيحي مضلِّل (`employee-clients-page.tsx`)
كان النص يقول «تظهر هنا سجلاتك الخاصة **والسجلات المشتركة** فقط» — وهذا لم يعد مطابقًا للسلوك بعد المنع الافتراضي. صار:

> «تظهر هنا سجلات جهات التواصل التي سجّلتها بنفسك فقط؛ لا تُعرض سجلات الموظفين الآخرين ولا السجلات المشتركة.»

### 2.5 تحديث التعليقات التوثيقية
حُدّثت تعليقات `contact-registry.ts` (ترويسة الملف، `registryOwnerFields`) لتوضيح قاعدة المنع الافتراضي، بدلًا من وصف COMPANY بأنها «مشتركة ظاهرة للجميع».

> ملاحظة: لم تُعدَّل سياسات العملاء العاديين (`ClientSample`) ولا قواعد الموافقة/التخصيص.

## 6. قيود الخصوصية (واجهة أمامية مقابل أمان حقيقي)

**الحالة: `Not Implemented` (خلفيًا).**

- كل الفلترة تجري في المتصفح. البيانات «الخاصة» موجودة أصلًا في حزمة JavaScript/الذاكرة، ويمكن الوصول إليها مباشرة.
- لا يوجد API مُفلتر للملاك/الوسطاء، ولا تفويض على مستوى الصفوف، ولا تدقيق وصول.
- السجل في الذاكرة فقط: كل السجلات غير البذرية تُفقد عند إعادة التحميل.
- دالة `companyContactsFor` غير المستخدمة تُعيد سجلات COMPANY دون فحص مستخدم — يجب حذفها أو تقييدها بالمدير مستقبلًا.
- دُرج تفاصيل العقار للموظف ما زال يعرض قسم «الموظفون المتابعون» (أسماء الموظفين + ملاحظات المتابعة). إن احتوت هذه الملاحظات على تفاصيل تفاوض خاصة، فهي قناة تسريب متبقية — خارج نطاق جهات التواصل لكن تستحق المراجعة.
- الوصف الحرّ للعقارات القديمة لا يخضع للتنقيح؛ المعالجة الحالية تعتمد على عدم حقن أرقام حساسة فيه.

**الخلاصة:** لا يمكن الادّعاء بأن البيانات الخاصة محمية من الوصول المباشر للمتصفح أو من استدعاء الـ API. هذه **مطابقة سلوكية للقاعدة**، وليست أمانًا.

## 12. متطلبات الخلفية المستقبلية (للإنتاج)

1. **جدول جهات التواصل الخلفي** مع `ownerUserId` (مفتاح خارجي إلى المستخدم) و`scope` وعلاقات `propertyId`.
2. **نهايات API مُفلترة على الخادم** تُعيد فقط السجلات المصرّح بها حسب دور المستخدم وملكيته — الفلترة الحالية في المتصفح ليست حماية.
3. **تفويض على مستوى الصفوف/السياسات** (ABAC/RBAC) يفرض: المدير يرى الكل، الموظف يرى ملكه فقط.
4. **إخفاء بيانات الاتصال الخاصة من استجابات API** لغير المخوّلين (أو حجب الحقول حتى الطلب المخوّل).
5. **خدمة رفع وتخزين ملفات** للصورة الواحدة (بلا معرض/روابط/فيديو)، مع تخزين دائم وربط بالعقار.
6. **تدقيق وصول (Audit log)** لكل مشاهدة/تعديل لبيانات الاتصال الخاصة.
7. **استمرارية سجل جهات التواصل** بدل الحالة في الذاكرة.
8. **إزالة/تقييد** الأدوات المساعدة غير المقيّدة (`companyContactsFor`) وإزالة تسريب الأرقام من أي نص حرّ على مستوى المكوّنات.
