## 1. مسار المصادقة الحالي

`JwtAuthGuard.canActivate` لكل طلب غير عام:

1. اختيار التوكن: كوكي `accessToken` إن وُجد، وإلا `Authorization: Bearer` فقط عند غياب الكوكي (منع غموض المصدر).
2. `jwt.verifyAsync` مع issuer/audience/secret/exp.
3. التحقق من الشكل: `sub` نصي غير فارغ، `exp` رقم، `sid` نصي، و`role ∈ {OWNER, MANAGER, EMPLOYEE}`.
4. **قراءة الجلسة والمستخدم** (موضع الاستعلامين):
   - `RefreshToken` حسب `id = sid` (مفتاح أساسي).
   - `User` المرتبط (role, isActive, authVersion).
5. الفحوص:
   - `session.userId === payload.sub`
   - `revokedAt` فارغ (تسجيل الخروج/الإبطال الفوري)
   - `expiresAt > now`
   - `user.isActive`
   - `user.role === payload.role`
   - `payload.av ?? 0 === user.authVersion`
6. تعيين `request.user = { id, role, sessionLineageId: session.lineageId }`.
7. أي خطأ → `401 Invalid or expired access token`.

### لماذا كان الاستعلامان ضروريان؟

- `RefreshToken`: التحقق من وجود الجلسة نفسها، عدم إبطالها، وانتهائها، وربطها بالمستخدم (`userId`) وسلالة الجهاز (`lineageId`).
- `User`: الصلاحية الحالية للحساب (`role`)، حالته (`isActive`)، وإصدار الأمان (`authVersion`) — لا تُؤخذ أبدًا من التوكن.

## 4. التغيير

**الملف:** `apps/backend/src/auth/guards/jwt-auth.guard.ts`

```sql
SELECT rt."userId", rt."revokedAt", rt."expiresAt", rt."lineageId",
       u.role, u."isActive", u."authVersion"
FROM "RefreshToken" rt
JOIN "User" u ON u.id = rt."userId"
WHERE rt.id = $1::uuid
```

- استعلام قراءة واحد، مُعامَل بالكامل (`rt.id = ${sid}::uuid`).
- نفس الفحوص بنفس الترتيب ونفس `401`.
- `request.user` يُبنى من نفس الحقول.
- **بدون** تغيير توكنات/كوكيز/مخطط/جلسات.
- `authVersion` الخاص بصف `RefreshToken` لم يُستخدم سابقًا في الحارس، ولم يُضف (الحارس يستخدم `user.authVersion` فقط)، حفاظًا على السلوك.

**تحديث اختبار فقط:** `test/auth.spec.ts` (Prisma test double) أضيفت محاكاة `$queryRaw` التي تعيد صف الجلسة من نفس الخرائط، مع إبقاء محاكاة advisory lock. لم تتغيّر أي توكيدات سلوكية.
