## 1. الخطر المؤكد وسببه الجذري

### الخطر

كان بإمكان مدير مصادَق عليه تسجيل **أي عنوان HTTPS** كـ Web Push endpoint، ثم قيام الخادم بإرسال طلب HTTPS إليه عند كل إشعار. هذا يسمح باستخدام الخادم كوسيط SSRF لاستهداف:

- خدمات داخلية وعنوان loopback.
- شبكات خاصة (RFC1918 / ULA).
- link-local و169.254.169.254 (بيانات وصفية للسحابة).
- منافذ HTTPS داخلية غير متوقعة.
- إعادة توجيه إلى وجهات غير مصرّح بها (لو كانت المكتبة تتبع redirects).
- استنزاف الاتصالات عبر endpoints بطيئة أو غير محدودة.

### السبب الجذري

في `apps/backend/src/push/push.service.ts`:

1. `subscribe()` كان يتحقق فقط من `@IsUrl({ protocols: ['https'] })` في DTO، ثم يخزّن `dto.endpoint` كما هو.
2. `deliver()` و`sendTestToSelf()` كانا يمرران `subscription.endpoint` مباشرة إلى `webpush.sendNotification()`.
3. `web-push@3.6.7` يستخدم `https.request` مع `hostname` و`port` مأخوذين من الـendpoint، دون قائمة نطاقات أو فحص لعنوان IP.
4. لم تكن هناك مهلة اتصال صريحة، ولا تحقق من DNS عند الاتصال.

### تقييم الخطورة

- **الوصول:** مدير مصادَق فقط، والميزة تحتاج مفاتيح VAPID مُهيأة.
- **الأثر:** طلب POST مشفّر إلى وجهة يختارها المهاجم، مع عدم إرجاع جسم الاستجابة إلى المهاجم. الأثر الأساسي: SSRF واستكشاف/إزعاج الخدمات الداخلية، واحتمال استنزاف الموارد.
- **التصنيف قبل الإصلاح:** **HIGH** (SSRF مصادَق عليه)، وليس Critical لأن الاستجابة لا تُعاد ولا توجد بيانات اعتماد داخلية تُرسل تلقائيًا.

## 3. قائمة مزوّدي Push المسموحين وأسبابها

### مضيفون محددون (Exact)

| المضيف | المتصفح/الخدمة | المصدر |
|---|---|---|
| `fcm.googleapis.com` | Chrome وكل متصفحات Chromium (Edge Chromium، Opera، Samsung Internet) | توثيق Chrome الرسمي لـFCM Web Push |
| `updates.push.services.mozilla.com` | Firefox — إنتاج Mozilla Autopush | توثيق Mozilla Autopush الرسمي |
| `web.push.apple.com` | Safari على macOS/iOS | توثيق Apple وWWDC22 |

### نطاقات فرعية محدودة ومُثبّتة (Anchored, one-label)

| النمط | السبب |
|---|---|
| `^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?\.notify\.windows\.com$` | Microsoft WNS (Edge) تنشر `*.notify.windows.com` رسميًا، والعناوين الفعلية مثل `wns2-by3p.notify.windows.com` و`dm3p.notify.windows.com` تختلف حسب المنطقة |
| `^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?\.push\.apple\.com$` | Apple توثّق السماح بأي نطاق فرعي من `push.apple.com`؛ النطاق الفعلي `web.push.apple.com` |

**لماذا هذا ليس wildcard غير آمن؟**

- النمط مثبّت على نطاق يملكه المزوّد نفسه.
- يسمح بتسمية فرعية واحدة فقط، وليس أي عمق أو أي لاحقة.
- يرفض `notify.windows.com.attacker.example` و`evil-notify.windows.com.attacker.example`.
- لا يستخدم `includes()` أو بحثًا نصيًا.

المضيف `android.googleapis.com` (GCM القديم) **غير مسموح**: Chrome الحديث يستخدم FCM، وGCM القديم يحتاج مفتاح GCM غير مُهيأ في هذا المشروع. لا توجد اشتراكات حالية على هذا المضيف.

## 4. الحماية الفعلية على مستوى النقل (Transport-Level)

### 4.1 عند التسجيل

`PUT /push/subscriptions` يمر الآن عبر `parseAllowedPushEndpoint()` قبل أي كتابة:

- HTTPS فقط.
- المنفذ الافتراضي 443 فقط (يُرفض 80، 8443، 3000 وغيرها).
- رفض `username`/`password` المدمجين.
- رفض `#fragment`.
- رفض عناوين IP المباشرة IPv4 وIPv6، بما فيها الصيغ العشرية/السداسية التي يعيد محرك URL تطبيعها.
- رفض المضيفات المشوّهة، والمسافات، ومحارف التحكم، والشرطة العكسية.
- تطبيع اسم المضيف لحروف صغيرة، ورفض النقطة النهائية.
- التحقق من بنية كل label وطول النطاق.
- قائمة بيضاء صريحة كما في القسم 3.

### 4.2 قبل كل إرسال

`deliver()` و`sendTestToSelf()` يعيدان التحقق من `subscription.endpoint` عبر نفس الدالة. الاشتراك القديم غير المسموح:

- **لا يُحذف تلقائيًا**.
- يُتخطى مع تسجيل تحذير يحتوي **معرّف الاشتراك فقط**.
- لا يولد طلبًا خارجيًا.

### 4.3 التحقق عند الاتصال ومنع DNS Rebinding

أُنشئ `SAFE_PUSH_AGENT` كـ`https.Agent` يحمل `lookup` مخصصًا:

1. يُستدعى `lookup` **عند إنشاء كل اتصال TLS**، وليس فقط عند التسجيل.
2. يعيد التحقق من أن المضيف ضمن القائمة المسموحة.
3. يحل DNS مرة واحدة باستخدام `all: true` (Happy Eyeballs).
4. يرفض الطلب إذا كان **أي** عنوان ناتج غير عام — وليس فقط العنوان المختار.
5. يعيد نفس العناوين التي تحققت إلى Node، فيتصل Node بها مباشرة. لا توجد إعادة تحليل DNS بين التحقق والاتصال، وهذا يغلق DNS rebinding.
6. TLS SNI والتحقق من الشهادة يظلان على اسم المضيف الأصلي، وليس على عنوان IP.
7. `keepAlive: false` لضمان إعادة التحقق عند كل إرسال.

### 4.4 العناوين المحظورة

يشمل الحظر:

- IPv4: `0.0.0.0/8`, `10/8`, `100.64/10` (CGNAT)، `127/8`, `169.254/16` (بما فيها 169.254.169.254)، `172.16/12`, `192.0.0/24`, `192.0.2/24`, `192.168/16`, `198.18/15`, `198.51.100/24`, `203.0.113/24`, `224/4`, `240/4`, والبث العام.
- IPv6: `::/96` (غير محدد + IPv4-compatible + loopback)، `64:ff9b::/96` و`64:ff9b:1::/48` (NAT64)، `100::/64`, `2001::/32` (Teredo)، `2001:2::/48`, `2001:10::/28` و`2001:20::/28` (ORCHID)، `2001:db8::/32`, `2002::/16` (6to4)، `fc00::/7` (ULA)، `fe80::/10`، `ff00::/8`.
- كل صيغ IPv4-mapped IPv6 (`::ffff:...`) تُرفض صراحةً، بما فيها العناوين التي تبدو عامة.

### 4.5 إعادة التوجيه

`web-push@3.6.7` لا يتبع redirects: يستخدم `https.request` مباشرة ثم يعتبر أي استجابة خارج 2xx فشلًا. لا يوجد أي كود يتبع `Location`. أُضيف اختبار يثبت أن استجابة 302 تُعامل كفشل إرسال واحد إلى نفس الـendpoint الأصلي، دون طلب ثانٍ.

### 4.6 المهلات

- مهلة DNS: **5 ثوانٍ**.
- مهلة طلب HTTPS: **10 ثوانٍ** (تُمرر إلى `web-push` وتُفعّل على socket).
- لا proxy مخصص؛ لا استخدام لمتغيرات بيئة proxy.

### 4.7 السجلات

- لا تُسجّل الـendpoint الكامل ولا `p256dh` ولا `auth`.
- عند فشل الإرسال يُسجّل معرّف الاشتراك + رمز الحالة/الخطأ فقط (`HTTP 302`, `ENOTFOUND`, …).
- عند رفض endpoint قديم: معرّف الاشتراك فقط.

## 5. الحفاظ على الوظائف الحالية

- مسار `PUT /push/subscriptions` كما هو، والاستجابة `{ subscribed: true }` كما هي.
- إلغاء الاشتراك كما هو، مع إبقاء إمكانية إزالة اشتراك قديم غير مسموح.
- الملكية المرتبطة بـ`userId` و`lineageId` لم تتغير.
- إشعارات المدير والموظف (in-app + push) لم يتغير مسارها.
- الاشتراك الحالي في قاعدة التطوير تم فحصه للقراءة فقط: **مضيفه `fcm.googleapis.com`**، وهو مسموح، ولم يُحذف أو يُعدّل.
- لا حذف تلقائي لأي اشتراك بسبب القائمة الجديدة.
- خدمة الإشعارات والـbadges والتنقل بالنقر لم تتغير.

## 8. المخاطر المتبقية

1. **صيانة قائمة المزوّدين:** إذا أضاف مزوّد نطاقًا جديدًا أو غيّر اسمه، يجب تحديث القائمة. النطاقات الفرعية محدودة بعمق واحد؛ إذا احتاج مزوّد مستقبلًا نطاقًا متعدد المستويات، يلزم تعديل مدروس.
2. **GCM القديم:** غير مسموح. لا يستخدمه Chrome الحديث، ولا توجد اشتراكات حالية عليه في قاعدة التطوير.
3. **بيانات قديمة غير صالحة:** الاشتراكات القديمة غير المسموحة تُتخطى ولا تُحذف، وقد تبقى في الجدول حتى يقوم المستخدم بإعادة التسجيل أو تنظيف إداري.
4. **DNS/OS resolver:** نعتمد على resolver النظام مع مهلة 5 ثوانٍ. لا يوجد DoH أو تثبيت IP مسبق؛ الحماية الأساسية هي التحقق عند الاتصال بنفس الإجابة المستخدمة.
5. **خدمات Push ذاتية الاستضافة:** غير مدعومة دون إضافة نطاقها للقائمة؛ خارج نطاق المتصفحات المدعومة حاليًا.
6. **بيئة اختبار حقيقية:** لم تُجرَ اتصالات خارجية فعلية أثناء الاختبارات (حسب المطلوب)؛ اختبار الشبكة الحقيقي يبقى في بيئة staging بموافقة المالك.
7. **حدود المعدل:** هذه المهمة لا تغطي rate limiting لمسار `/push/test` أو التسجيل؛ تبقى ضمن قائمة تقوية الإنتاج.

## 9. الخلاصة

- ثغرة SSRF عبر Web Push كانت **مؤكدة** وتم إغلاقها.
- الحماية مطبقة في طبقتين: التحقق عند التسجيل، والتحقق عند الاتصال الفعلي مع تثبيت نتيجة DNS.
- لا توجد redirects متبعة، ولا وصول لعناوين loopback/private/metadata، ولا تسجيل للـendpoints أو المفاتيح.
- متصفحات Chrome/Edge/Firefox/Safari محفوظة عبر قائمة المزوّدين الرسمية.
- الاختبارات والفحوصات ناجحة، والتغييرات غير ملتزمة.
