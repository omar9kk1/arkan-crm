## 2. الثغرة التي تمت معالجتها

**GHSA-q7qp-rjg7-q26m — Multer DoS عبر `fileFilter` غير متزامن بعد انتهاء الطلب**

- **النطاق المتأثر:** `multer >=2.0.0 <2.5.0`.
- **الإصدار المثبت سابقًا:** 2.4.0.
- **التصنيف:** High — CVSS 3.1: **7.5** (`AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`).
- **الأثر:** طلب multipart مُصمم يمكن أن يترك `fileFilter` غير متزامن معلّقًا بعد إغلاق الطلب، ما يسبب استهلاك موارد/تعليق الخدمة.
- **ملاحظة قابلية الاستغلال في هذا المشروع:** الكود الحالي لا يستخدم `fileFilter` مخصصًا؛ يمرر الملف مباشرة إلى `FileInterceptor('image')`. لذلك كان الخطر الفعلي محدودًا، لكن الترقية تُغلق الثغرة على مستوى المكتبة ولا تعتمد على افتراضات الاستخدام.

## 3. طريقة الترقية والتوافق

### الطريقة المختارة

أُضيف **root npm override ضيق** في `package.json`:

```json
"overrides": {
  "@nestjs/platform-express": {
    "multer": "2.5.0"
  }
}
```

ثم:

1. أُعيد بناء قفل الحزمة بحيث يكون `node_modules/multer` = **2.5.0**.
2. نُفّذ **`npm ci` نظيف** من القفل (بعد إيقاف خوادم التطوير المحلية التي كانت تحتجز ملف Prisma DLL).
3. أُعيد توليد Prisma Client بأمر `npm run db:generate` (لا يمس قاعدة البيانات) لأن `npm ci` أزال المخرجات المولدة.
4. تم التحقق من النسخة الفعلية:
   - `node_modules/multer/package.json` = **2.5.0**.
   - `node_modules/@nestjs/platform-express` = **11.2.8**.
   - `node_modules/@nestjs/core` = **11.2.3**.

### أدلة التوافق

- Multer 2.5.0 يحمل **نفس** `engines` و`dependencies` الخاصة بـ2.4.0.
- الواجهة المستخدمة من Nest هي `multer().single('image')` عبر `FileInterceptor`، وهي واجهة مستقرة في سلسلة 2.x.
- لم يتغير أي كود في `PropertiesController` أو `FilesService`.
- جميع اختبارات الرفع والصور والاستبدال والاعتماد نجحت على 2.5.0.
- لم يتم الانتقال إلى Nest 12 أو Multer 3 alpha.

### ملاحظة `npm ls`

`npm ls multer` يعرض النسخة **2.5.0**، لكن npm يضيف علامة `invalid: "2.4.0"` لأن `@nestjs/platform-express` يعلن تثبيتًا دقيقًا على 2.4.0. هذا سلوك متوقع من npm عند override يتجاوز نطاق تثبيت دقيق، وليس ثغرة: النسخة المثبتة فعليًا 2.5.0، و`npm audit` لم يعد يرى Multer. سيختفي هذا التحذير تلقائيًا عندما يصدر Nest 11.x يعتمد Multer ≥2.5 أو عند ترقية Nest 12 بموافقة منفصلة.

## 5. الحماية الحالية التي تم الحفاظ عليها

- مصادقة عالمية + ملكية الموظف للعقار.
- `FileInterceptor('image')` — ملف واحد فقط.
- حد **5MB** لكل صورة (`MAX_IMAGE_BYTES`) على مستوى Multer وعلى مستوى الخدمة.
- حدود multipart:
  - `files: 1`
  - `fields: 10`
  - `fieldSize: 1MB`
  - `parts: 20`
  - `headerPairs: 2000`
- التحقق من محتوى الصورة الفعلي (magic bytes) وليس الامتداد أو `Content-Type`.
- إعادة ترميز Sharp وإزالة EXIF/XMP/IPTC.
- حدود البكسل/الأبعاد/الحجم النهائي.
- تخزين خاص، مفاتيح عشوائية، ومنع path traversal.
- تقديم الصور عبر endpoint مُصرَّح فقط.
- استبدال الصورة يمر بمراجعة المدير ولا يمس الصورة الأصلية قبل الاعتماد.
- حذف/استعادة/حذف نهائي وسلوك الإشعارات لم تتغير.

## 7. المخاطر المتبقية

1. **علامة `npm ls`:** `invalid: "2.4.0"` تبقى ظاهرة لأن Nest 11.2.8 يثبّت Multer 2.4.0 بدقة. النسخة الفعلية 2.5.0، والاختبارات والـaudit يؤكدان ذلك. الحل الدائم: Nest 11.x يحدّث تثبيته أو Nest 12 بموافقة.
2. **Prisma High:** 3 تحذيرات متبقية في `npm audit` خارج نطاق Multer؛ تتطلب ترقية Prisma 7 Major.
3. **قيود الاختبار:** اختبارات الرفع تستخدم بيانات معزولة وملفات صغيرة؛ لا يوجد اختبار شبكة خارجي أو حمل غير محدود.
4. **الرفع المقطوع:** تم اختباره محليًا ولم يُسقط الخادم؛ لا يمكن ضمان سلوك كل وكيل/شبكة إنتاجيًا دون مراقبة.
5. **`npm ci` وPrisma:** في هذه البيئة احتاج `npm ci` إلى إعادة توليد Prisma Client قبل تشغيل الاختبارات. هذا لا يغير قاعدة البيانات، لكنه يجب أن يكون جزءًا من pipeline النشر إن لم يكن postinstall يفعله تلقائيًا.
